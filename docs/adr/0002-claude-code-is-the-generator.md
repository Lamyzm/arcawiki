# ADR-0002. 생성 주체는 Claude Code 다. 웹에는 LLM 을 붙이지 않는다

- 상태: 채택
- 날짜: 2026-08-11

## 맥락

위키 내용을 누가 언제 만드느냐에 세 가지 선택지가 있었다.

- **A. 미리 만들어 둔 것만 보여준다** — 친구는 이미 생성된 문서를 읽는다.
- **B. 친구가 물어보면 그때 생성한다** — 웹에 LLM 을 붙인다.
- **C. 둘을 섞는다** — 없으면 그때 만들어 저장한다.

B 와 C 는 친구가 쓸 때마다 API 비용이 발생하고, 그러면 인증·요청 제한·남용 대응이
처음부터 설계에 들어가야 한다.

## 결정

**A.** 그리고 더 중요한 것: 생성하는 LLM 은 웹에 붙는 서비스가 아니라
**터미널에서 돌아가는 Claude Code 세션 자신**이다.

```
Claude Code ──생성/정제──> PostgreSQL ──읽기 전용──> 웹 (친구)
```

웹 애플리케이션은 Postgres 를 읽어서 보여주기만 한다. API 키를 갖지 않고,
LLM 을 호출하지 않는다.

## 이유

- 친구 사용량이 지출로 이어지지 않는다. 비용은 생성할 때 한 번뿐이다.
- 웹에서 인증·요청 제한·남용 대응이 필요 없어진다. 공개해도 금전적 위험이 없다.
- 생성 품질을 사람이 그때그때 확인하고 고칠 수 있다. 자동 파이프라인이 조용히
  이상한 문서를 쌓아두는 일이 없다.
- 오케스트레이션 계층(Prefect, 워커, 큐, Batch API)이 통째로 필요 없다.
  Claude Code 세션이 곧 오케스트레이터다.

## 결과

- 위키 커버리지는 내가 세션을 돌린 만큼만 늘어난다. 자동으로 자라지 않는다.
- 미리 만들어 두지 않은 주제는 친구가 찾을 수 없다. 이 공백을 웹에서 어떻게
  다룰지는 별도 결정이 필요하다.
- 증분 업데이트도 사람이 돌리는 작업이 된다. 크론으로 자동화하려면 그때
  다시 판단한다.
- 웹 스택 선택이 자유로워진다. LLM 연동 요건이 없으므로 조회에 편한 것이면 된다.

## 대안

- **B (웹에 LLM)**: 사용량이 곧 지출. 친구가 몇 명이든 비용이 예측 불가.
  인증·제한 설계가 선행돼야 한다. 기각.
- **C (혼합)**: 같은 질문은 한 번만 과금된다는 장점이 있으나 구현이 가장 복잡하고
  여전히 비용이 열려 있다. 지금 단계에서는 과하다. 기각.
