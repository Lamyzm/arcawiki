# 로라 쓰는 법

> **원문 108건 → 이 문서 하나** · 주장 283개 · 정리 2026-08-14

로라(LoRA)는 **모델 위에 얹었다 뗐다 할 수 있는 작은 추가 학습 파일**이다. 캐릭터·그림체·의상·포즈·구도처럼 **프롬프트만으로는 안 나오는 것**을 로라로 해결한다.

이 문서는 **로라를 쓰는 법**만 다룬다. 로라를 직접 굽는 법(학습)은 범위 밖이다. 쓰는 쪽에서 가장 많이 막히는 것은 세 가지다 — **호출 문법이 툴마다 다르다**, **로라가 프롬프트를 잡아먹는다**, **남의 그림을 따라했는데 재현이 안 된다.** 순서대로 다룬다.

## 이건 언제 쓰는 것인가
<small>⚠️ 2025-05 기준 · 근거 2건</small>

**프롬프트만으로 안 나오는 것이 있을 때 쓴다.** 그게 전부다.

전형적인 사례 — `upside-down` 태그를 넣고 성행위 태그를 넣으면 엉뚱하게 **여자 엉덩이를 높게 들어 찍어누르는 자세**가 많이 나온다. 태그 조합으로는 원하는 자세가 안 나오므로 **전용 컨셉 로라를 쓴다**(137644242, 2025-05, 추천 63).

로라로 해결하는 것들:

| 종류 | 예 |
|---|---|
| **캐릭터** | 모델이 모르는 캐릭터, 학습량이 적은 캐릭터 |
| **그림체(스타일)** | 특정 작가체, 애니메이션 화면 느낌 |
| **의상·소품** | 한복처럼 프롬프트로 한계가 있는 옷 |
| **포즈·구도·체위** | 태그 조합으로는 안 나오는 자세 |
| **퀄리티 보정** | 디테일·안정화용 (아래 별도 항목) |

**여러 개를 동시에 쓸 수 있다.** 로라는 원본 모델은 그대로 두고 학습된 부분만 더하는 구조라 **모듈처럼 붙였다 뗐다 할 수 있다**(68914565). 실제로 캐릭터 + 그림체 + 의상 + 포즈를 한 번에 꽂는 것이 일반적이다.

## 원리 — 왜 파일이 작고 왜 여러 개를 쓸 수 있나
<small>⚠️ 2023-02 기준 · 근거 1건</small>

알고 쓰면 뒤의 항목들이 전부 이해된다. 수학은 건너뛰어도 된다(68914565, 2023-02, 논문 기준 정리).

**LoRA = 낮은 rank 의 행렬을 이용해 거대 모델을 튜닝하는 방법.**

- `W0` 가 원래 모델(d×k 행렬), `ΔW` 가 파인튜닝 후 원래 모델과의 차이다.
- Dreambooth 처럼 `ΔW` 를 전부 계산하면 VRAM 도 많이 먹고 결과물이 새 모델 자체라 저장공간도 먹는다.
- LoRA 는 **`ΔW` 를 `B×A` 의 행렬 곱으로 나누고 B 를 d×r, A 를 r×k 로** 만든다. 파라미터 수가 `d×k` 에서 `(d+k)×r` 로 줄어든다(r << d, k). **그래서 파일이 작다.**

**여러 개를 동시에 쓸 수 있는 이유**:

> 원본 모델 `W0` 는 가만히 두고 `BA` 만 학습하며, 합칠 때도 `W0` 에 학습된 `BA` 만 더하면 된다. 그래서 파인튜닝 결과가 **모듈처럼 붙였다 뗐다 할 수 있다.**

`<lora:이름:가중치>` 를 여러 개 써서 로라를 여러 개 불러올 수 있는 것이 이것 때문이다.

원 논문: Microsoft, 2021-10, *LORA: LOW-RANK ADAPTATION OF LARGE LANGUAGE MODELS* (`https://arxiv.org/pdf/2106.09685.pdf`)

## 호출 문법 — WebUI 와 ComfyUI 가 다르다
<small>2025-09 기준 · 근거 2건</small>

**A1111 / Forge / reForge** — 프롬프트에 직접 쓴다.

```
<lora:이름:가중치>
예) <lora:ponyv6_noobV1_2_adamW:1>
```

로라를 불러오면 **프롬프트에 이 문자가 반드시 남는다.** 이 사실이 뒤에 나오는 "재현 가능성 판별"의 근거가 된다.

**ComfyUI — 프롬프트 칸의 `<lora:...>` 문법이 먹히지 않는다.**

> ComfyUI 에서는 프롬프트 칸에 `<lora:이름:0.4>` 라고 써도 **적용되지 않으며 로라 로더 노드로 따로 불러와야 한다**(147183795 댓글).

이걸 모르면 "분명히 로라를 썼는데 아무 변화가 없다"에서 며칠 헤맨다. ComfyUI 를 쓴다면 `LoraLoader` / `Power Lora Loader (rgthree)` / `LoRA Stacker` 중 하나를 쓴다. → [ComfyUI 쓰는 법](comfyui.md)

**ComfyUI 로라 관련 흔한 에러** — `LoRA Stacker` 에서 `string indices must be integers, not 'str'` 가 뜨면, `./ComfyUI\custom_nodes\efficiency-nodes-comfyui` 폴더를 **완전히 삭제**하고 ComfyUI Manager 에 등록된 **`Efficiency Nodes for ComfyUI Version 2.0+`** 로 재설치한다. **이름은 같지만 완전히 다른 커스텀 노드**다(110068034 댓글). 로라 키워드가 안 먹히면 합치는 순서를 바꿔 보라(로라 키워드는 기본이 꺼져 있다).

**NAI** 는 캐릭터 로라를 쓸 수 없고 대신 바이브(Vibe) 기능이 있다(147183795 댓글). → [NovelAI](nai.md)

## 남의 그림을 따라했는데 다르게 나오는 이유 — EXIF 로 판별하기
<small>2025-09 기준 · 근거 1건</small>

채널에서 가장 자주 나오는 질문의 답이다(147183795, 2025-09, 추천 48. reForge/WebUI 기준).

**핵심 판별법** —

> 로라를 많이 썼는데 **프롬프트에는 로라를 쓴 흔적이 전혀 없으면** ComfyUI 에서 만들었거나 Civitai 사이트/외부 사이트에서 만든 이미지일 확률이 높다. reForge 에서 로라를 불러오면 프롬프트에 `<lora:ponyv6_noobV1_2_adamW:1>` 같은 문자가 **반드시 남기 때문**이다. 이런 정보가 없으면 ComfyUI 에 이미지를 올려 워크플로우가 있는지 확인하고, 없으면 **과감히 포기하라.**

| EXIF 상태 | 재현 가능성 |
|---|---|
| 모델·로라 정보가 있고 **프롬프트 안에 로라 호출문이 전부 있음** | **높다.** 그대로 적용하면 비슷하게 나온다 |
| 로라 옆에 가중치는 적혀 있는데 **프롬에 호출문이 없음** | Civitai 에서 뽑은 것 (댓글 보충) |
| 로라 정보가 없거나, 그림체는 화려한데 **프롬프트가 이상할 정도로 짧음** | 낮다 |
| `CIVITAI generator` 라고 적힘 | 직접 돌리면 크게 다른 경우가 많다 |

**로라 이름을 검색해도 안 나올 때**: Civitai 에 올린 제목과 로라 파일 이름이 다른 경우가 많다. **EXIF 로라 항목의 해시값을 그대로 Civitai 검색창에 넣으면 바로 뜬다.**

```
7a6cdc714921
```

같은 로라라도 버전이 여러 개면 파일 이름(예: `96YOTTEA-WAI` → v1.1 의 WAI 버전)으로 유추하고, 가장 확실한 방법은 직접 받아 파일 이름을 확인하는 것이다.

**ComfyUI 를 원문이 다루지 않는 이유**도 밝혀 뒀다 — 같은 프롬프트·로라·모델을 써도 **워크플로우에 따라 그림체가 미묘하게 다른 경우가 많고** 워크플로 자체가 복잡하기 때문이다. 개인 워크플로우를 만들고 거기에 로라를 추가하는 방식을 권한다.

EXIF 를 읽는 도구는 [자원 — 받는 곳 모음](resources.md).

## 로라가 프롬프트를 잡아먹을 때 — LoRA Block Weight
<small>2026-07 기준 · 근거 7건</small>

**"자기주장이 강한 로라를 넣으면 프롬프트를 거의 무시한다"** 는 문제의 정면 해법이다(71644460, 2023-03).

로라의 **일부 블록만 적용**한다. 예를 들어 얼굴에 영향을 주는 블록만 살리고 나머지는 빼는 식이다.

설치: `https://github.com/hako-mikan/sd-webui-lora-block-weight` 후 재시작.

**문법** — 기존 `<lora:이름:가중치>` 뒤에 `:프리셋` 을 덧붙인다.

```
<lora:로라이름:0.2:OUTALL>
```

**블록 프리셋 목록** (댓글 확인):

```
NONE, ALL, INS, IND, INALL, MIDD, OUTD, OUTS, OUTALL, ALL0.5
```

**찾는 법**: X/Y/Z plot 에서 `X Types` 를 `original weight` 로 체크하고 `X Values` 에 위 프리셋 목록을 통째로 붙여넣은 뒤 `Y Types` 는 none 으로 두고 돌린다. 프리셋별 결과가 격자로 나오면 마음에 드는 것을 골라 그것만 적고 실행한다.

**댓글의 더 간단한 실사용법** — X/Y plot 을 거치지 않고 프롬프트에 바로 섞어 쓸 수 있다.

```
<lora:로라이름:0.5:INALL>, <lora:로라이름:0.5:MIDD>, <lora:로라이름:0.3:OUTS>, <lora:로라이름:0.2:OUTALL>
```

다만 `<lora:로라이름:1:XYZ>` 형태 그대로는 안 되고 **실제 프리셋 이름**을 넣어야 동작한다는 보고가 있다.

**알려진 오류**: `ValueError: could not convert string to float: 'ALL0.5'` — 프리셋 이름을 가중치 자리로 잘못 파싱하는 경우다.

글쓴이가 "100%는 아니고 아는 부분만 적었다"고 명시했고 코랩 환경 기준이다.

---

### 블록이 정확히 몇 개이고 이름이 무엇인가

프리셋만 쓰면 되지만, **수치를 직접 적으려면 개수와 순서를 알아야 한다** (71353884 계열, 2023-03).

```text
BASE, IN01, IN02, IN04, IN05, IN07, IN08, MID,
OUT03, OUT04, OUT05, OUT06, OUT07, OUT08, OUT09, OUT10, OUT11      ← 17개
```

LyCORIS/LoCon·LoHa 는 **26블록짜리도 있고** kohya_ss 산은 그것도 지원한다.
17블록 로라는 **미기입 수치를 1 로 치므로 17개만 적으면 된다.**

**쓰는 법 세 가지**

| 방식 | 문법 | 특징 |
|---|---|---|
| 수치 직접 | `<lora:이름:1:0,0,1,0,...>` | **EXIF 에 설정값이 남는다** |
| 이름/Block ID | `<lora:이름:1:CU1>` · `<lora:이름:1:IN04>` | 프리셋은 Weights setting 에서 직접 정의할 수 있다 |
| XYZ 위임 | `<lora:이름:1:XYZ>` | XYZ Plot 에서 설정. **Disable 을 XYZ 로 바꿔야 동작한다** |

**⚠️ 이름 함정 — 여기서 대부분 에러가 난다**

```text
MID   라고 적으면 에러      →  이 확장은 MID 를 M00 으로 쓴다
OUT3  라고 적으면 에러      →  OUT03 처럼 두 자리로 쓴다
```

**Block ID 기입 문법**

| 표기 | 뜻 |
|---|---|
| `OUT03, OUT04` | **콤마 = 개별 항목** (따로따로 처리된다) |
| `OUT03 OUT04` · `OUT03-OUT11` | **스페이스/대시 = 한 덩어리** |
| `NOT OUT03-OUT11` | 제외 |
| `1,1,1,...` | ⚠️ **숫자열을 Block ID 칸에 적으면 인식하지 못한다** |

`values` 는 블록에 곱해지는 배율(예: `0,0.25,0.5,0.75,1`)이고 **1 을 넘기면 에러는 안 나지만 결과가 쓰레기가 된다.**
Block ID 는 켜고 끌 블록을 정하는 것이라 **값 없이 단독으로 쓰면 에러**가 난다.
총 생성 장수는 `X x Y x Z` 다 — values 5개 x Block ID 1개 x Original Weights 3개 = 15장.

> 당시 버그 하나 — **hires. fix 를 함께 쓰면 LoRA 가 동작을 멈췄다.** 제보 후 수정됐다.

### ANIMA 로라는 28블록이다

ANIMA 로라는 **블럭 0~27, 총 28개 레이어**로 펼쳐진다.
**스타일 로라가 아닌데도 그림체에 영향을 주거나 의도치 않은 것이 튀어나오는 ANIMA 로라가 많아서**,
어느 블럭이 원하는 변화를 주는지 확인할 필요가 있다 (171479837, 2026-05).

- 원하는 구간만 켜는 커스텀 노드가 공유돼 있다 — 파라미터는 `start_block` / `end_block`
  (`https://drive.google.com/file/d/1b_bRZDEA_WfRPxiaBnIeM8t3yKayNMf-/view`)
- **인스파이어 팩에 블럭필터 기능이 기본 내장돼 있으나 ANIMA 용 프리셋이 없다** *(댓글)*

[ANIMA](anima.md) 의 "highres 가 뭉개질 때 — 세팅이 아니라 로라를 의심하라" 와 같은 문제를 다루는 도구다.

### 호출 한 줄로 블록을 지정하는 옛 문법

2023년에는 로라 호출 뒤에 **블록 이름을 직접 붙이는** 표기가 쓰였다 (72250546 · 73207701).

```text
<lora:red hair highlight v3:1:HAIR>
                          ↑ 적용 블록을 HAIR 로 지정
```

머리카락 하이라이트 로라를 **머리 블록에만** 걸어 다른 부분에 번지지 않게 한 사례다.
지금은 LoRA Block Weight 확장의 프리셋으로 같은 일을 한다.

### 곁가지 — 태그 '사이' 값이 필요할 때는 임베딩을 합성했다

로라가 아니라 **임베딩** 쪽 기법인데 같은 글에서 나온다 (72250546, 2023-03).
`embedding inspector` 로 **두 태그의 임베딩 벡터를 섞어 새 토큰**을 만들면 기존 태그 사이의 값을 쓸 수 있다.

```text
deepblue = blue + black          (진한 남색 머리)
mela2    = medium + large        → (mela2 breasts:1.45) 처럼 쓴다
```

danbooru 태그가 아닌 이름이 프롬프트에 보이면 이런 자작 임베딩일 수 있다.

### 보조 로라의 가중치 운용 — 음수를 쓴다

```text
<lora:add_detail:0.8> <lora:_L2090:0.3> <lora:add_saturation:1.5> <lora:add_brightness:-2>
```

`add_saturation` 은 **1.5 로 올려 채도를 높이고**, `add_brightness` 는 **`-2` 라는 음수**를 줘서 밝기를 반대로 낮춘다 (77356160, 2023-05).

> **LoRA 가중치에 음수를 넣으면 학습된 효과가 역방향으로 작동한다.** 슬라이더류 로라를 쓸 때 그대로 통하는 규칙이다.

### 얼굴만 이식하기, 그리고 난수 자리

블록별 가중치의 대표적인 실사용이 **캐릭터 로라에서 얼굴만 가져오는 것**이다 (1건, 2023-02).

```text
OUTDD:1,0,0,0,0,0,0,0,0.5,1,1,0.5,0,0,0,0,0     ← 로라의 얼굴만 이식된다
```

숫자 자리에 **난수 기호**를 넣으면 그 블록만 무작위화된다.

| 기호 | 범위 |
|---|---|
| `R` | 0 ~ 1 |
| `U` | -1.5 ~ 1.5 |

```text
ROUT:1,1,1,1,1,1,1,1,R,R,R,R,R,R,R,R,R          ← OUT 레이어만 랜덤
```

2023-01-31 업데이트로 **마이너스 가중치에도 효과가 생겼다.**
슬라이더로 조정하고 싶으면 `https://github.com/bbc-mc/sdweb-merge-block-weighted-gui` 를 쓴다.

## 로라를 많이 쓰면 생기는 일 — 개수와 슬롯 관리
<small>2025-12 기준 · 근거 2건</small>

**로라 개수는 공짜가 아니다.**

**증상 — 컨트롤넷 오픈포즈를 안 따라간다.** ComfyUI + ILXL 에서 오픈포즈 이미지를 넣었는데 포즈를 따라하는 시늉만 하는 경우, 첫 번째 대처가 **"로라를 많이 쓰면 이런 일이 생긴다. 로라 개수를 줄이거나 찐빠를 내는 원인 로라를 찾아내라"** 다(156251545, 2025-12). → [컨트롤넷](controlnet.md)

글쓴이 추정: 로라나 체크포인트에 특정 포즈가 강하게 학습되어 있어서로 보인다.

**슬롯을 용도별로 나눠 두면 원인을 찾기 쉽다.** 실사용 캐릭터 워크플로우의 6슬롯 구성(153880353, 2025-11):

| 슬롯 | 용도 |
|---|---|
| 캐릭터 | 학습량이 많아 로라가 존재하는 캐릭터 |
| 스타일 | 그림체 (작가·애니메이션 계열) |
| 복장 | 프롬프트만으로 한계가 있는 옷 |
| 컨셉 | 포즈와 겹치지만 인물이 많이 나오거나 만화 형식인 로라 |
| 포즈 | 프롬프트로 한계가 있는 포즈 |
| 보조 | 여유 공간 (바바리걸 + 코트 안 복장을 섞을 때 등) |

## 트리거 워드 관리 — 많아지면 못 외운다
<small>⚠️ 2023-02 기준 · 근거 1건</small>

로라가 많아지면 **트리거 워드와 세부 사항을 하나하나 기억하는 것은 불가능하다.** 원문의 표현으로는 **"트리거 단어를 꿰고 있지 않는 한 대 클릭의 시대가 열린다"**(70646351, 2023-02, 추천 88).

**방법 — 로라 파일과 같은 이름의 `.txt` 를 만들어 정보를 적어 둔다.**

```
3Character - [Overwatch] Kiriko.txt
https://civitai.com/models/8088/kiriko-overwatch-lora
Version: v1
Recommended Weight:
Recommended Size:
Recommended Words:
, hair between eyes,
For default clothes:
, white kimono, red skirt,
Add Negative:
, headgear,
Trigger Words:
, kiriko \(overwatch\), green hair, ponytail, facial mark, fox mask, half mask,
```

적어 두는 항목: 첫 줄에 **다운로드 URL**, `Version:` 받은 시점의 버전(같은 URL 에서 버전을 바리에이션으로 쓰는 경우 구분용), `Recommended Weight:` 추천 가중치, `Recommended Size:` 추천 해상도, `Recommended Words:` 목적별 추천 단어, `Add Negative:` 함께 넣을 네거티브, `Trigger Words:` 트리거 태그.

**검색 방법**: SublimeText(`https://www.sublimetext.com/`)를 깔고 `File > Open Folder` 로 로라 폴더를 연다. **`Ctrl+P`** 를 누르면 바로가기 창이 뜨는데 로라 이름을 입력하면 매칭되는 파일만 보이고, txt 를 선택해 열면 트리거 워드를 바로 확인할 수 있다.

폴더 분류는 **Style / Pose / Others / Character** 네 개를 썼다.

**요즘 대안**: Civitai 메타데이터를 읽는 확장이 같은 역할을 한다 — A1111 의 로라 카드 설명란, ComfyUI 의 `LoraInfo` 노드 등. 이 글은 그런 도구가 없던 시절의 수작업 방식이지만 **관리해야 할 항목이 무엇인지**는 그대로 유효하다.

## 함정 — rank 와 alpha
<small>⚠️ 2023-02 기준 · 근거 1건</small>

로라를 받아 썼는데 **아무 효과가 없을 때** 의심할 것 중 하나다. 만드는 쪽 이야기지만, 받아 쓰는 쪽도 알아 두면 "이 로라는 고장 났다"를 판별할 수 있다.

논문은 `ΔW` 에 `α/r` 을 곱한다.

- `1/r` 로 나누는 이유: `BA` 의 각 성분은 r 개 독립변수 정규분포의 합이라 분포가 `N(0, r)` 이 되므로, `1/r` 을 곱해 표준정규분포로 되돌린다.
- `α` 를 곱하는 이유: `1/r` 때문에 rank 가 높은 LoRA 는 학습이 느려지므로, `α` 로 원하는 방향으로 더 빨리 학습시킨다.
- **Microsoft 공개 당시에는 `α` 를 1 로 고정**했고 예제도 `r=4`, `r=8` 이라 `1/r` 의 영향이 작았다.

**SD 로라에서 벌어진 사고**:

> SD 로라 학습에서 `r=128` 이상을 쓰는 모델이 유행했는데, 논문대로 `α=1` 로 두고 `1/r` 을 그대로 두는 바람에 **실제 학습률이 1/128 로 토막나 몇몇 high rank 모델에서 underflow 가 발생했다(로라가 작동하지 않음).**

**해결책 두 가지** —

1. 논문 예제대로 `r=4`, `r=8` 등 low rank 를 쓰면서 `α=1` 로 두고 learning rate 만 조절한다.
2. high rank 면 **`α = r`** 로 두어 스케일링 효과를 아예 없애고 learning rate 만 조절한다.

댓글 실측: **실제로 잘 학습된 로라들의 메타데이터를 보면 대부분 `r=128, α=128`** 로 두고 lr 만 조정한다. `rank` 는 학습 설정의 `network dimension` 값이다.

즉 **받은 로라의 메타데이터에 `r=128, α=1` 이 찍혀 있으면 그 로라 자체가 고장 났을 가능성**을 의심할 수 있다.

## 로라가 안 먹는 것 같을 때 — 로라보다 체크포인트를 먼저 의심하라
<small>2026-07 기준 · 근거 3건</small>

스타일 로라를 넣었는데 **효과가 거의 없다면 로라를 잘못 만든 것이 아니라 체크포인트가 로라를 씹고 있는 것**일 수 있다.

3D 카툰렌더링 스타일 로라 제작자가 겪은 일이 그대로 남아 있다. 처음 `WAI` 체크포인트에서 테스트했을 때
효과가 거의 없어 로라를 잘못 구운 줄 알았는데, 사실은 **WAI 자체의 그림체가 너무 강해 로라가 묻힌 것**이었다.
**NoobAI 계열로 바꿔 테스트하니 효과가 확실했다.**

| 체크포인트 | 같은 로라의 효과 |
|---|---|
| `WAI v140` | 효과 미비 — 로라를 잘못 만든 줄 알았다 |
| `NAI-XL` (NoobAI 계열) | 직빵 |

강도도 체크포인트마다 다르게 잡아야 한다.

```text
0.6  → 2D 느낌이 좀 더 남는다
1.0  → 3D 느낌이 많이 강해진다
※ 체크포인트에 따라 '적용치' 자체가 상당히 다르다
```

같은 원리가 그림체 로라 평가 전반에 통한다 — **베이스를 바꿔 가며 평가해야 한다.**
ANIMA 그림체 로라를 `아니마 미적 향상 1.1` · `wai-anima` · `anima base` 세 판에서 비교해 본 배포자도
앞의 둘이 목표 그림체에 가장 가까웠다고 적었고, 2023년 한복 로라도 오렌지 계열에서는 잘 나오는데

## 굽기 준비 ① — 무엇을 베이스로 구울 것인가 (첫 관문)
<small>2026-07 기준 · 근거 5건</small>

학습을 시작하기 전에 **어느 모델 위에서 구울지**부터 정해야 한다. 여기서 갈리면 뒤의 수치를 아무리 잘 잡아도
남의 모델에서 안 나온다. 채널에서 가장 많은 로라를 배포한 제작자가 댓글에서 직접 답한 기준이 있다.

| 목적 | 무엇으로 굽나 | 왜 |
|---|---|---|
| **남에게 공유할 것** | `illustriousXL_v1.1` 같은 **순정 원본 베이스** | **일러스트리어스가 웬만한 병합 모델 대부분에 들어가 있어 호환성이 가장 좋다.** 순정 illustriousXL 로 학습해야 다른 병합 모델에서도 최대한 잘 나온다 |
| **나만 쓸 것** | **내가 그림 뽑을 때 쓰는 그 모델** | 어차피 그 모델에서만 쓸 것이므로 |
| 내가 쓰는 모델이 **학습에 나쁠 때** | 그 **병합 모델에 들어간 베이스 모델**을 찾아 그것으로 | 병합본은 학습이 잘 안 되는 경우가 있다 |

버전은 `0.1` 보다 `1.1` 이다 — 요즘 병합 모델들이 1.0 기준으로 만들어지는 추세라 0.1 로 만든 로라는
잘 안 나올 때가 있다 (`https://civitai.com/models/1252206/illustrious-xl-11`).

### ⚠️ 학습 베이스 모델 ≠ 그림을 만드는 모델

입문자가 가장 자주 헷갈리는 곳이라 배포자들이 글마다 못 박아 둔다.

```text
LoRA Base Model    illustriousXL_v1.1     ← 로라를 '만들 때' 쓴 바탕. 그림을 뽑는 모델이 아니다
Checkpoint Model   WaiNSFWillustrious V140 ← 실제로 그림을 뽑는 모델
```

로라는 **같은 계열(여기서는 Illustrious/SDXL) 체크포인트에서만** 제대로 동작한다.
ANIMA 판 시리즈는 `anima-base-v1.0` 으로 굽고 `waiANIMA_v10Base10` 으로 뽑으며, 둘은 서로 호환되지 않는다.

### 원본이 3D 인 캐릭터라면 ANIMA 쪽이 낫다

같은 제작자가 게임 '화이트데이' 의 같은 캐릭터 4인을 두 번 구웠다 — 2025-05 에는 `illustriousXL_v1.1` 로,
2026-07 에는 `anima-base-v1.0` 으로. 그 결론은 **원본이 3D 인 캐릭터는 Illustrious 계열보다
ANIMA 계열에서 훨씬 학습이 잘 된다**는 것이다.

## 굽기 준비 ② — 데이터셋 만들기 (스타일 로라 교본)
<small>2026-06 기준 · 근거 5건</small>

로라 품질은 데이터셋에 수렴한다. `qiandaiyiyu` 그림체 로라(2025-08) 배포글이 그 과정을 통째로 적어 두어

```text
1) 수집        약 680장
2) 큐레이션    → 217장 (5~13MB 급 고화질만 남김)
3) 시기 자르기 2024-07-27 까지의 그림만  ← 최신 그림체만 안정적으로 재현하려고

6) 지우기      말풍선 · 텍스트 · 작가 이름 · 서명 · 트위터 아이디를 포토샵으로 제거
```

## 굽기 준비 ③ — 학습률: 재현과 범용성의 맞바꿈
<small>2026-06 기준 · 근거 1건</small>

그림체 로라를 구울 때 학습률(learning rate)을 얼마로 잡느냐는 **원본을 얼마나 빡세게 베낄 것인가**의 문제다.
같은 데이터로 학습률만 바꿔 세 판을 구워 비교한 배포글이 있다.

| 학습률 | 성격 |
|---|---|
| `2e-05` ~ `4e-05` | **범용 그림체**로 쓸 것 |
| `6e-05` | **원본을 빡세게 재현**할 것 |

**학습률이 높을수록 원본과의 유사도가 올라가는 대신 범용성이 떨어진다.**
배포자 본인의 권고는 *"하나만 쓸 거면 `4e-05` 판을 베이스로 깔고 다른 로라·작가 태그를 섞는 것"* 이다.

실제로 그 커스텀 로라 단독으로는 목표 그림체의 7~9할까지 잡히고, 여기에 다른 그림체 로라를 1:1 로 섞으니
거의 같아졌다고 한다(다만 가슴이 크게 나오는 부작용이 붙었다).

> 이 수치는 **ANIMA 계열 그림체 로라 기준**의 감각이다. SDXL·Illustrious 계열의 kohya 파라미터는
> 아래 "굽기 L — 파라미터 한 벌" 을 본다.

## 굽기 A — ComfyUI 에서 그림 1장으로 1분 (2026-02, 지금 가장 빠른 길)
<small>2026-02 기준 · 근거 1건</small>

ComfyUI 안에서 **그림 1장만 넣고 실행 버튼 한 번**으로 태깅 → 학습 → 저장 → 테스트 이미지 출력까지 끝내는 워크플로다. Illustrious(IL) 계열 기반 (161876070, 2026-02, 추천 50).

### 사전 준비가 핵심이다

**1) Kohya_ss 설치** — `https://lykos.ai/` (Stability Matrix)로 받아 **C: 또는 D: 드라이브 바로 아래**에 두고(**경로에 한글 금지**) 포터블 모드로 설치한다. 설치 화면에서 스킵 후 `Add package → Training → NVIDIA → Install` 순, 약 3분.

```
C:\Data\Packages\kohya_ss   또는   D:\Data\Packages\kohya_ss
```

**2) `accelerate.exe` 를 손으로 복사한다 — 이걸 안 하면 동작하지 않는다.**

```
복사할 것 :  .\kohya_ss\venv\Scripts\accelerate.exe
붙일 곳   :  .\kohya_ss\sd-scripts\venv\scripts\accelerate.exe
```

> 붙일 곳 경로는 **존재하지 않는다.** `venv` 폴더와 그 아래 `scripts` 폴더를 **손으로 만들어 줘야 한다.**

### 워크플로 구성

```
이미지 업로드 → WD14 Tagger 자동 태깅 → 태그가 긍정 프롬프트로 자동 삽입
             → realtime 학습 노드 → 학습된 LoRA 로드 → KSampler → 이미지 저장
```

### 설정값

| 항목 | 값 |
|---|---|
| `images_path` | **비워 둔다** (여러 장 학습할 때만 폴더 경로 지정) |
| `sd_scripts_path` | `D:\Data\Packages\kohya_ss\sd-scripts` |
| `ckpt_name` | IL1.0 권장 — `https://huggingface.co/Liberata/illustrious-xl-v1.0/resolve/main/Illustrious-XL-v1.0.safetensors` |
| 학습 스텝 | `50` |
| 학습률 | `0.001` |
| LoRA 랭크 | `32` |
| `vram_mode` (학습 해상도) | `1024` — VRAM 이 모자라면 512 나 768 로 낮춤 |
| `keep_lora` | `true` |
| `no_half_vae` | `false` |
| WD14 Tagger Threshold | `0.35~0.5` 가 가장 잘 됐다 |

## 굽기 C — 태그 정리: 무엇을 지우고 무엇을 남기나
<small>⚠️ 2025-02 기준 · 근거 8건</small>

**이 문서에서 가장 중요한 항목이다.** 세 글이 서로 다른 도구(Civitai · kohya_ss · 로컬 GUI)를 쓰면서 **같은 원칙에 도달했다.**

### 원칙

> **로라는 이미지에 붙은 태그가 곧 트리거 워드가 된다.** 태그가 남아 있으면 학습기는 "이건 태그로 지정된 **별도 요소**구나"라고 인식하고, 태그를 지우면 "이건 **이 캐릭터의 일부**구나"로 인식한다.

### 지울 것 — 캐릭터의 신체·고유 특징

| 예 | 지우지 않으면 |
|---|---|
| `horns` (한쪽 뿔이 특징) | 나중에 **뿔 없는 그림**이 나오고, 매번 `horns` 를 프롬프트에 넣어야 한다 |
| 눈 색 · 머리 색 · 가슴 크기 | 캐릭터 이름만으로 안 나온다 |
| 말 귀 · 갈색 단발 · 적색 눈 · 바보털 | 같은 이유 (69024839 도 동일하게 "캐릭터 이름 태그에 흡수시킨다"고 적는다) |

반대로 **지우면** "뿔이 있는데 태그가 없으니 이 캐릭터의 일부구나"로 인식해 **거의 반드시 뿔이 나온다.**

같은 원리로 71341748 은 이렇게 정리한다 — **(a)** 내가 프롬프트로 쓰지 않을 태그(`highres`, `simple background`), **(b)** 로라를 쓸 때 어차피 항상 같이 넣을 태그(`1girl`, `solo`, 캐릭터 고유의 `pink hair`·`blue eyes`), **(c)** 표정 태그(`open mouth`, `smile`, `blush`, `looking at viewer`)를 지운다.

### 남길 것 — 배경 · 자세 · **의상**

> **의상 태그는 지우지 않는다.** 지우면 그 의상이 캐릭터 특징처럼 **붙박이가 되어 다른 옷을 입히지 못하게 된다.** 의상이 부족하게 나오면 그때 프롬프트로 보충하면 된다 (129031066 댓글에서 정리된 결론).

즉 지우는 기준은 **"어떤 상황에서도 절대 빠지면 안 되는 것"** 이다. 뿔·고정 머리장식이 여기 해당하고, 옷은 해당하지 않는다.

### 여러 의상을 한 로라에 담을 때 나는 사고

> A의상 이미지와 B의상 이미지가 **둘 다 `pink hair` 태그를 가지고 있으면**, `pink hair` 에 두 의상 정보가 섞여 저장되는 사고가 난다 (71341748).

그래서 공통 특징 태그를 지워 캐릭터 이름으로 흡수시키는 것이 더 중요해진다.

### 예외 — 지우면 안 되는 것

`empty eyes`, `ahegao` 처럼 **기본 프롬프트로 구현이 어려운 것**은 태깅해 둬야 나중에 부를 수 있다.

### 태거가 잘못 붙이는 태그

`virtual_youtuber`, `ponytail`, `star_hair_ornament` 처럼 해당 없는 태그를 붙이는 경우가 있으니 **Exclude tags 에 넣어 걸러야 한다** (72213859).

### 태거 threshold

**1 에 가까울수록 확실한 태그만 붙는다.**

| 학습 대상 | threshold |
|---|---|
| 일반 · 그림체 · 배경 | `0.35` |
| 사물 · 캐릭터 | `0.85` |
| ComfyUI 1장 학습 | `0.35~0.5` 가 가장 잘 됐다 |


### 태그를 지운다는 것의 뒷면 — 트리거 워드를 의도적으로 만드는 법

같은 원리를 거꾸로 쓰면 **원하는 디자인만 부르는 트리거 워드를 직접 만들 수 있다** (71353884 댓글, 2023-03).

```text
모자 쓴 데이터  50%  →  그 데이터에만  straw hat  태그를 준다
모자 안 쓴 데이터 50% →  태그 없음
결과 : straw hat 이 '정확히 그 디자인의 모자' 를 부르는 트리거가 된다
```

**한쪽에만 태그를 붙이면 그 태그가 그 요소의 스위치가 된다.** 위의 "지울 것/남길 것" 은 이 원리의 두 극단이다.

### 그림체 학습은 태깅을 안 해도 된다

> **캐릭터 학습은 태깅을 하고, 그림체 학습은 태깅을 안 해도 잘 나온다** *(댓글)*.

이유는 위와 같다 — 그림체는 **모든 이미지에 공통으로 들어 있는 것**이라 특별히 태그로 분리해 줄 필요가 없다.

### 데이터셋 파일 규칙과 자동 태깅

```text
1.png  ↔  1.txt        같은 파일명의 쌍이어야 한다
1.txt  내용 :  태그, 태그, 태그
```

태그 파일이 없으면 자동 태깅을 쓴다 (68948357, 2023-02).

| 태거 | 형식 |
|---|---|
| `BLIP_Captioning` | **자연어** 형식 |
| `WD_1_4_Tagger` | **단부루 태그** 형식 |

### 이미지를 긁어올 때 — Gelbooru 검색 규칙

| 표기 | 뜻 |
|---|---|
| `rating:g` / `rating:s` | 건전 / 약후 |
| `rating:q` / `rating:e` | nsfw(야스X) / nsfw(야스O) |
| 공백 대신 `_` | `long_hair` |
| 태그 앞에 `-` | 제외 |

> ⚠️ **부루 스크래퍼로 통째로 긁는 것은 권장되지 않는다** — 퀄리티가 제각각이고 컨셉 그림이 섞여 오기 때문이다.
> **특정 작가 그림체 로라가 아니면** 손으로 고르는 편이 낫다 (68948357).

배경이 투명한 머그샷·설정화가 많으면 학습 전에 **투명도를 없애는 편이 편하다** *(댓글)*.

## 굽기 D — rank 와 alpha: 도구가 바뀌어도 통하는 원리
<small>2026-02 기준 · 근거 4건</small>

2023년 실험 보고서지만 **rank/alpha/learning rate 의 관계 설명은 지금 어떤 트레이너를 쓰든 그대로 유효하다** (69024839, 2023-02 / 71607955, 2023-03).

위의 '**함정 — rank 와 alpha**' 항목이 *받아 쓰는 쪽*에서 본 설명이라면, 여기는 *굽는 쪽*에서 본 것이다.

### 왜 alpha 를 건드려야 하나

> **kohya_ss 방식에서 실효 학습률은 `alpha/rank` 에 비례해 스케일된다.** 그래서 **alpha 를 1 로 고정한 채 rank 만 올리면 학습률이 토막 나서 높은 rank 에서 학습이 제대로 되지 않는다.**

실험에서 실제로 rank 가 높아질수록 승부복의 세부(노란 스웨터 안 검은 셔츠)가 재현되지 않았다.

### 처방

`alpha/rank` 를 **일정하게 고정**하고 **learning rate 로만 조절**한다.

| 방식 | 설명 |
|---|---|
| `alpha = rank` | 스케일링 효과를 아예 없앤다. **국룰**이며 잘 만든 로라들의 메타데이터도 대부분 이쪽 |
| `alpha/rank = 1/4` 고정 | 실험에서 쓴 값 (rank4/alpha1, 16/4, 64/16, 128/32) — 높은 rank 에서도 복장이 잘 나왔다 |
| `alpha = 1` 로 두겠다면 | learning rate 를 **더 높게** 잡아야 한다 |

> **댓글 주의** — dim 64 에 alpha 64 로 맞추면 **학습이 터진다**(이미지가 뿌옇거나 모자이크처럼 나옴)는 제보가 있었고, 답은 **그림체 학습은 캐릭터보다 낮은 학습률이 필요하므로 alpha 를 dim 과 같게 둘 거면 lr 을 `1e-5~1e-6` 까지 낮추라**는 것이었다.

### 과적합이 보이면

실험에서 `alpha/rank` 를 고정하니 높은 rank 에서 **살짝 뿌옇게(과적합 기미)** 나왔는데, **로라 가중치를 낮춰서는 해결되지 않았고** CFG scale 을 `6.5 → 5 → 3.5` 로 낮추니 깨짐 없이 잘 나왔다.

### rank 는 얼마가 적당한가 — 두 자료가 다르다

**캐릭터라면 낮아도 된다** (69024839) —

> **rank 4(4.6MB)와 rank 128(144MB)의 차이를 구분하기 어렵다.** 굳이 rank 를 올려 32배 용량을 낭비할 이유가 없다.

| rank | 용량 |
|---|---|
| 4 | 4.6MB |
| 16 | 18MB |
| 64 | 72MB |
| 128 | 144MB |

**대상이 복잡하면 올려야 한다** (84182288 의 난이도별 권장 랭크표) —

| 난이도 | 대상 | rank |
|---|---|---|
| A | 특이한 옷·디테일 없는 단순한 여성 캐릭터 | 4~8 |
| B | 특이한 얼굴·머리·색·의상을 가진 여성 | 4~16 |
| C | 날개·갑옷·꼬리 등 추가 요소가 있는 정교한 캐릭터 | 8~32 |
| D | 인간형 퍼리, 실사 인간 | 32~64 |
| E | 더 특이한 형태 | 64 |
| F | 동물, 포켓몬·드래곤, 인간형 로봇, 화려한 갑옷 | 64~128 |
| G | 건담·EVA 같은 인간형 메카, 외계인, 악마 | 128 |
| H | 비인간형 로봇, 몬스터, 곤충, 실사 동물 | 128~192 |
| I | 섬뜩한 괴물 | 192~256 |

**모순이 아니라 범위가 다른 이야기다** — "캐릭터는 저랭크로 충분"은 위 표의 A~B 에 해당하고, 대상이 복잡해질수록 필요한 랭크가 커진다. 2026년 ComfyUI 1장 학습이 **랭크 32** 를 기본값으로 쓰는 것도 그림체까지 담기 위해서다.

고랭크와 저랭크의 차이를 **PNG 와 JPG 정도**로 비유한 댓글도 있다.

## 굽기 E — 수치의 뼈대: step · batch · repeat · epoch 와 학습률
<small>⚠️ 2025-02 기준 · 근거 7건</small>

실행 환경(2023년 코랩)은 낡았지만 **학습 용어 정의는 지금 어떤 트레이너를 쓰든 그대로 통한다** (71607955, 2023-03).

### 용어

| 용어 | 뜻 |
|---|---|
| **batch size** | 모델이 **한 번에 동시에** 학습하는 이미지 개수. 1이면 느리고 VRAM 을 적게 먹으며, 6이면 빠르지만 VRAM 을 많이 먹는다 |
| **step** | batch 가 한 번 이루어진 횟수. **학습의 단위** |
| **repeats** | 한 epoch 안에서 데이터셋 전체를 한 바퀴 도는 **루프 횟수.** 루프마다 이미지 순서는 무작위로 바뀌지만 한 루프에 같은 이미지가 두 번 학습되지는 않는다 |
| **epoch** | 가장 큰 단위 |
| **iteration** | `이미지 수 / batch size` |

```
총 step = repeats × epochs × (이미지 수 / batch size)
```

> **총 step 만으로 품질과 시간을 추측하는 것은 오차가 너무 크다**고 원문이 못박는다. batch size, learning rate, 학습 방법, 베이스 모델에 따라 전부 달라지기 때문이다. ("하급 3000 / 중급 5000 / 상급 10000 이 국룰"이라는 말이 돌지만 작성자 본인이 신뢰도가 낮다고 밝힌다.)

### 학습률

> **batch 1 기준 unet `1e-4`, text encoder 는 그 절반인 `5e-5`.** 배치가 **2배가 될 때마다 학습률도 2배**로 올린다 (작성자의 나중 갱신).

VRAM 때문에 배치를 못 올리면 `gradient accumulation` 을 2로 주면 배치와 에포크에 2가 곱해진다. 71341748 도 같은 취지로 "VRAM 이 허용하는 만큼 배치를 올리고 이때 러닝레이트도 배치 크기만큼 곱하라"고 적는다.

### 데이터셋 장수 — 자료마다 다르다

| 자료 | 권장 |
|---|---|
| 84182288 (2023-08) | 캐릭터 **10~50장** / 스타일 100~4000장 / 컨셉 50~2000장 |
| 129031066 (2025-02) | 한 의상당 **20~40장** (40장으로도 과적합 안 남) |
| 71607955 (2023-03) | **50~150장, 100장이 적당.** 많다고 좋지 않다 |
| 71341748 (2023-03) | 최소 30장, **50장 이상 안정권**, 200장 초과는 의미 없어 좋은 것만 150장 추림 |

겹치는 구간은 **20~50장**이다. 거기서 시작하면 된다.

### flip(좌우 반전) 증강 — 세 글이 같은 경고를 한다

> 다양성을 늘리고 과적합을 막지만, **가르마가 한쪽인 캐릭터·오드아이·한쪽에만 있는 장식**처럼 좌우가 중요한 대상에는 **절대 쓰면 안 된다.** 뒤집힌 샘플이 하나라도 있으면 AI 는 "반대로 그려도 되는구나"라고 배워 버린다.

### loss 로 과적합을 판정할 수 없다

> 0.1 에서 0.06 까지 잘 수렴한 학습이 과적합으로 망하기도 하고, 0.12 에서 논 학습이 더 잘 나오기도 했다. 다만 **loss 가 1.14 이상으로 계속 높으면 learning rate 를 낮춘다** (71341748). 71607955 댓글도 "loss 1.4→1.1 로 수렴해도 과적합이 나고 0.7~0.8 로 끝난 로라가 멀쩡한 경우가 있다"고 같은 말을 한다.

### optimizer

| 이름 | 성격 |
|---|---|
| `AdamW` | 가장 안정적 |
| `AdamW8bit` | AdamW 의 메모리·계산 부담을 낮춘 것. **GTX 10번대는 이걸 쓰면 안 된다** |
| `Lion` · `SGD` | 초기 학습이 빠르지만 local minima 에 갇힐 수 있음 |
| `DAdapt` | 학습률과 weight decay 를 자동 조정 |
| `Adafactor` | 스케줄러도 adafactor 로 맞춰야 하고 메모리는 줄지만 성능 저하 |


### 정규화 이미지를 쓸 때의 계산

```text
repeats × 데이터셋 장수   >=   정규화 repeats × 정규화 장수
```

**넘는 것은 안 쓰이지만 부족하면 과적합이 난다.** `reg repeats` 는 보통 **1 로 둬야 계산이 편하다** (71353884, 2023-03).

| 데이터셋 설정 | 대응하는 정규화 장수 |
|---|---|
| 10 repeats × 10 epoch, 50장 | 500장 |
| 100 repeats × 1 epoch, 50장 | 5000장 |

```text
실사 https://github.com/JoePenna/Stable-Diffusion-Regularization-Images
애니 https://huggingface.co/datasets/waifu-research-department/regularization
```

정규화 이미지가 무엇을 하는 것인지는 아래 "굽기 F" 의 드림부스 항목에 있다 —
**기존에 배운 걸 잊지 말라고 알려 주는 것**이다.

### noise offset — 어두운 그림이 안 나올 때

| | |
|---|---|
| 왜 있나 | **Stable Diffusion 이 어두운 음영 표현을 잘 못하는 문제**를 완화한다. 어두운 분위기·그림자·색채 일관성이 좋아진다 |
| 값 | 일반 `0.05` · **권장 `0.1`** · 최대 `1` (**높일수록 이미지가 깨진다**) |

위 "굽기 B" 의 Civitai 트레이너가 화풍별로 `0.00~0.20` 을 권하는 것과 범위가 겹친다.

### ⚠️ loss 로 과적합을 판정할 수 있는가 — 두 자료가 어긋난다

**이 문서 안에서 정면으로 갈리는 지점이다. 양쪽을 다 적어 둔다.**

| 쪽 | 주장 | 출처 |
|---|---|---|
| **판정할 수 있다** | **loss 가 `0.15~0.13` 대에서 놀다가 특정 epoch 를 기준으로 `0.09`·`0.07` 로 내려가면 과적합**이다. 몇 step 몇 epoch 에서 그러는지 메모해 두면 다음에 조절할 수 있다 | 71353884 (2023-03) |
| **판정할 수 없다** | `0.1` 에서 `0.06` 까지 잘 수렴한 학습이 과적합으로 망하기도 하고 `0.12` 에서 논 학습이 더 잘 나오기도 했다. `1.4 → 1.1` 로 수렴해도 과적합이 나고 `0.7~0.8` 로 끝난 로라가 멀쩡한 경우가 있다 | 71341748 · 71607955 댓글 (2023-03) |

**어긋나 보이지만 겹치는 부분이 있다** — 양쪽 다 *"loss 절대값으로는 못 본다"* 에 동의하고,
앞쪽 주장이 말하는 것은 값이 아니라 **급격한 하락이라는 변화의 모양**이다.
어느 쪽이든 **결론은 같다 — 에포크마다 저장해 실제로 뽑아 보고 고른다.**

> **더 확실한 판별은 loss 가 아니라 결과물에 있다** *(댓글)* —
> **로라 가중치 1 에서 이미지가 잘 나오는 것이 정상이고, 이상하면 과적합난 것이다.**

### 학습률 — 대상에 따라 갈린다

위의 batch 기준 값(`unet 1e-4` / `TE 5e-5`)과 별개로, **무엇을 학습하느냐로 나눈 값**도 있다 (72241015, 2023-03).

| 대상 | Unet LR |
|---|---|
| **캐릭터** | `5e-4` |
| **그림체** | `1e-4` |

Text encoder LR 은 Unet 의 **1/2~1/5** 이고 **그림체 학습에서는 별로 중요하지 않다.**
스케줄러는 **`cosine with 3 restarts`** 가 과적합 방지에 체감이 좋았고
`constant` · `constant with warmup` · `cosine` 도 무난하다.

*(그림체 쪽 학습률이 더 낮은 것은 위 "굽기 D" 댓글의 *"그림체 학습은 캐릭터보다 낮은 학습률이 필요하다"* 와 같은 이야기다.)*

### 다 구운 뒤 — 무엇을 고를 것인가

에포크마다 저장해 놨다면 고르는 절차가 정해져 있다 (72241015).

```text
1. 마지막 에포크를 가중치 0.7 로 넣고 최다 태그로 뽑아 본다
2. X/Y/Z 스크립트  X value 에  -01, -02, -03      → 에포크 비교
3. X/Y/Z 스크립트  X value 에  0.5, 0.6, ... 1.0  → 가중치 비교
```

**가중치 1 에서 정상으로 나오는 에포크**를 고르면 된다.

## 굽기 F — 임베딩 · 하이퍼네트워크 · 드림부스 · 로라, 무엇이 다른가
<small>⚠️ 2023-08 기준 · 근거 4건</small>

2023년 초 글이지만 **지금도 입문자에게 가장 잘 통하는 개념 정리**다. 모델(체크포인트)을 **뇌**로 놓고 본다 (68353136, 2023-01, 추천 50).

| | 비유 | 무엇을 하나 | 한계 |
|---|---|---|---|
| **임베딩** (Textual Inversion) | **전자책** | AI 가 모르는 단어를 **자기가 이미 아는 지식으로 어떻게 만들지** 알려 주는 설명서 | 모델이 아예 모르는 개념은 만들 수 없다. 좋은 임베딩을 학습시키는 난이도가 높다 |
| **하이퍼네트워크** | **최면** | 모델이 **이미 아는 것을 잘 안 꺼내 놓을 때** 사고방식을 비틀어 자주 꺼내게 만든다 | 모르는 개념은 못 만든다. 지금은 거의 안 쓴다 |
| **드림부스** | **세뇌** | **뇌 자체를 개조**하므로 모르던 것도 알게 만든다. 성능이 가장 좋다 | 결과물이 모델 하나라 용량 부담이 크고 학습 VRAM 이 **최소 12GB · 실질 16GB · 권장 24GB** |
| **LoRA** | **세뇌 임플란트** (기억이 담긴 USB) | 드림부스 기반이되 **삽입할 일부 기억만** 담는다 | 최종 성능은 드림부스보다 떨어진다 |

**LoRA 가 이긴 이유** — 용량이 하이퍼네트워크와 비슷하거나 더 작고, 학습 난이도와 사양 요구가 낮으며, **개별 적용 강도 조절과 여러 개 동시 적용이 되고 병합해 새 모델을 만들 수도 있다.**

### 폴더와 호출 문법

| | 폴더 | 부르는 법 | 용량 |
|---|---|---|---|
| 임베딩 | `embeddings` | 프롬프트에 **파일명 그대로** (네거티브용이면 네거티브 칸에) | 1KB~1MB |
| 하이퍼네트워크 | `models/hypernetworks` | `<hypernet:파일명:1>` | 20MB~수백MB |
| **LoRA** | `models/lora` | `<lora:파일명:1>` | 하이퍼네트워크와 비슷하거나 더 작음 |
| 드림부스 결과 모델 | `models/Stable-diffusion` | 체크포인트로 로드 | 2~7.2GB |

(ComfyUI 는 프롬프트 문법이 아니라 로더 노드를 쓴다 → 위 '호출 문법' 항목)

### 조금 더 깊게 — QKV 찰흙 비유

하이퍼네트워크가 왜 그런 한계를 갖는지는 **Cross-attention 의 QKV** 로 설명된다 (62805139, 2022-11).

| | 비유 |
|---|---|
| **Q**uery | 이미지의 기저 정보 — **찰흙 같은 소재** |
| **K**ey | 텍스트·조건의 기저 정보 — **찰흙으로 뭘 만들지 명령하는 것** |
| **V**alue | 텍스트에서 이미지로 연결되는 정보 — **실제로 찰흙을 주무르는 것** |

Key 와 Query 의 상관 정도로 attention 밀도를 얻고, 그것으로 Value 를 수정해 결과를 낸다.

> **하이퍼네트워크는 Q 를 안 건드리고 KV 만 훈련한다.** 즉 "소재는 그대로 두고 무엇을 어떻게 만들지만 바꾸는" 셈이라, **애니풍을 실사로 바꾸는 것 같은 변화는 불가능하다.** (찰흙에 물감 대신 붓질로 그림을 그리겠다는 소리라는 비유가 붙어 있다.)

**댓글의 비유가 특히 잘 정리돼 있다** — 텍스추얼 인버전은 *"우리는 이것을 OO 라고 부르기로 약속했어요"* 라고 이름을 붙이는 것, 하이퍼넷은 기존에 그리던 방식에 딴지를 걸어 교정하는 것으로 **그릴 줄 아는 범위 안에서만** 교정되며, 드림부스는 뇌에서 일부 세포를 적출하고 새 세포를 이식하는 것이고 그때 **기존에 배운 걸 잊지 말라고 알려 주는 것이 정규화 이미지**다. 사실상 **완전히 새로운 것을 배우는 것은 드림부스뿐**이다.

> 드림부스가 여전히 유용한 곳도 있다 — 혼합용 전체 모델 생성, 시리즈 스타일 드림부스를 만든 뒤 그 위에서 캐릭터 학습, 일반적인 스타일 학습. *"드림부스가 LoRA 보다 낫다"는 인상은 잘 훈련된 드림부스만 기억해서 그런 것*이고, 잘 훈련된 LoRA 는 비슷한 범위에서 비견되며 **지속 가능성은 훨씬 낫다** (84182288).

## 굽기 G — 구울 때 자주 막히는 곳
<small>⚠️ 2023-08 기준 · 근거 6건</small>

### 결과 파일이 `.safetensors` 가 아니라 `.json` 으로 나온다

**여러 명이 같은 증상을 겪은 유명한 함정이다.**

> **`LoRA` 탭이 아니라 `Dreambooth` 탭으로 학습한 것이다** (69186437 댓글, 2023-02).

드림부스는 결과물이 로라 파일이 아니므로 당연히 다른 것이 나온다. 탭을 확인하고 다시 돌린다.

### `Error no kernel image is available for execution on the device at line 167 ... bitsandbytes\csrc\ops.cu`

**`Use 8bit adam` 체크를 풀면 해결된다.** 파스칼·Titan XP·GTX 10번대 계열은 **xformers 도 함께 꺼야** 한다. 대신 매우 느려져서 40장 학습에 두세 시간이 걸린다 (70243793 · 68205055).

> ⚠ 같은 `no kernel image is available` 문구라도 **A1111 로 그림을 뽑는 중**이라면 원인이 다르다 — RTX 50(블랙웰)에 master 브랜치를 쓴 것이다 → [오류 해결](troubleshooting.md)

### `AssertionError: when caching latents, either color_aug or random_crop cannot be used`

`Cache latents` 와 `Random crop` 은 **둘 중 하나만** 켤 수 있다. 이미지를 비율에 맞게 잘라 놨으면 `Random crop` 을 끄고, 대충 모아 놨으면 `Cache latents` 를 끈다 (69186437 댓글 · 68205055).

### `No data found` / `mean ar error (without repeats): nan` / `train_data_dir must be the parent of folders with images`

**폴더 구조 문제다.** 지정한 이미지 폴더 **바로 아래에는 이미지가 있으면 안 되고** `[반복수]_[토큰] [클래스]` 형식의 폴더만 있어야 한다.

```
img/100_sks girl/1.png
```

수동으로 만들지 말고 kohya GUI 의 `Tools / Folder Prepare` 에서 `prepare training data` → `copy info` 를 차례로 눌러 **자동 생성**시키는 편이 실패 확률이 낮다 (70243793 · 68205055).

### `RuntimeError: Error(s) in loading state_dict for UNet2DConditionModel: size mismatch ...`

`torch.Size([320, 768])` vs `[320, 1024]` 식의 불일치는 **SD1.x 기반인데 `v2` / `v_parameterization` 을 실수로 켠 것**이다. 끄면 해결된다 (70243793).

### `RuntimeError: CUDA out of memory` (학습 중)

배치 사이즈나 학습 해상도를 줄인다. 실제 사례: `Train batch size 10 → 1`, `Number of CPU 4 → 2`, `Network Rank 64 → 8`, `Network Alpha 1` (70243793).

### 학습이 `step 0` 에서 멈춘다

**batch size 를 1 로 낮추면 돌아가는 경우가 있다** (65776582 댓글, 2022-12).

### 페이징 파일 오류

`OSError: [WinError 1455]` / `exit status 3221225477` 는 **가상 메모리를 늘린다** → [오류 해결](troubleshooting.md)

### `missing key(s) in state_dict: text_model.embeddings.position_ids`

Civitai 에서 받은 것 중 **`CHECKPOINT MERGE` 유형은 학습 베이스로 안 되는 경우가 있다.** 이 오류가 뜨면 그것을 의심한다 (70243793 댓글).

### 설치 위치를 잘못 잡았다

> **Kohya 스크립트(`https://github.com/kohya-ss/sd-scripts`)는 WebUI 와 같은 위치에 설치하면 안 된다.** 라이브러리 버전이 달라 **WebUI 를 망가뜨리므로** 반드시 별도의 파이썬 가상 환경을 만들어야 한다 (84182288).

### (옛 기법) 학습 중 VAE 가 끼면 결과가 망가진다

하이퍼네트워크·임베딩 학습 이야기지만 사고 유형이 특이해서 남긴다.

> **VAE 가 적용된 상태로 학습하면 결과가 망가진다.** `unload VAE and CLIP` 을 체크하거나 VAE 파일 이름을 바꾸고 WebUI 를 재시작해서 VAE 가 개입하지 못하게 해야 하며, **수많은 사람이 이것 때문에 학습 시간을 통째로 날렸다** (60913615).

같은 글이 학습 시 `--medvram` 인자를 넣지 말라고도 강조한다(넣으면 결과가 눈에 띄게 나빠진다는 제보가 여럿).

### A. Cream LoRA Trainer — 준비물이 가장 적다

```bash
cd ComfyUI/custom_nodes
git clone https://github.com/vanila-cream/cream_lora_trainer
```

데이터셋 폴더 경로·체크포인트·트리거워드·로라 이름만 지정하고 실행하면 **캡션 생성 → 학습 → 샘플 생성**까지 자동이다.
`sd_scripts_path` 를 비워 두면 `ComfyUI\custom_nodes\comfyui-cream-lora-trainer` 안에 kohya 가 자동 설치된다
(실패하면 StabilityMatrix 로 깔고 `C:\kohya_ss\sd-scripts` 처럼 경로를 넣는다).

| 바꿀 수 있는 값 | 기본값 |
|---|---|
| `target_steps` | **1000** (범위 10~50000, 소규모 데이터셋은 **500~2000**) |
| `save_steps` | 100 (N스텝마다 중간 로라 저장, 0이면 최종만) |
| `learning_rate` | **0.0003** — U-Net 기준. **TE 학습률은 자동으로 1/10** |
| `lora_rank` | **32** (4~128, 권장 **16~64**) |
| `vram_mode` | Low VRAM 8GB+ 는 U-Net 만 / High VRAM 12GB+ 는 U-Net+TE |
| `batch_size` | 1 (Low VRAM 에서는 1 고정) |

고정값: `resolution 1024x1024` · `optimizer Adafactor` · `lr_scheduler constant_with_warmup` ·
`mixed_precision bf16` · `fp8_base true` · `noise_offset 0.0357`

> ⚠️ **한계 세 가지** — ① **SDXL(ILXL) 계열 전용**이라 ANIMA·Z-Image 는 그냥은 안 된다.
> ② **스타일(그림체) 로라는 잘 안 된다** — 캐릭터와 반대로 여러 캐릭을 그린 그 작가 그림을 모으고
> 캐릭터 외형을 **정확히 태깅**해야 하는 작업이라 이 노드의 자동 캡션 정제와 방향이 반대다.
> ③ 소규모 데이터셋에 **5000스텝을 걸었다가 2600스텝쯤에서 VRAM 부족으로 터진 보고**가 있다.

캡션 자동 정제가 무엇을 지우는지는 이 문서의 "굽기 C — 태그 정리" 절과 같은 원칙이다.

### B. 코햐 아니마 — ANIMA 로라는 이쪽

```text
https://github.com/Source2Spy/kohya_ss_anima
```

배포된 `아니마 toml 만들기.py` 를 메모장으로 열어 **세 줄만** 자기 경로로 고친다.

창에 폴더를 드래그하고 `TOML 생성하기` → `training.bat` 실행이면 `toml_list.txt` 순서대로 연속 학습된다.

> ⚠️ **데이터셋 폴더명과 그 상위 폴더명까지 경로 전체가 영문이어야 한다.** 한글이 들어가면 인식하지 못한다.

| 항목 | 값 |
|---|---|
| 데이터셋 | 캐릭터 **20장 이상** 권장 / 스타일은 **1000장 넘기지 말 것** |
| 이미지 크기 | 가로세로 **1080px 이상**이면 좋고 조금 작아도 된다 |
| 스타일 로라 + 수백 장 | toml 의 `epoch` 와 `max_train_epochs` 를 **둘 다 1** 로 (안 바꾸면 시간만 오래 걸리고 과적합 위험) |
| 학습 강도 | `img` 폴더의 `20_로라명` 앞 숫자(repeats). 20장 초과면 20 그대로, **20장 이하면 40~60** |
| 트리거워드 | 없음 — 캐릭터 로라는 **캐릭 외형 태그를 직접 적어야** 한다 |

**표시 스텝과 실제 총 스텝이 다를 수 있다** — 배치 2 에 표시 스텝 3000 이면 실제 총 스텝은 6000,
배치 4 면 12000 이 되는 경우가 있어 체감 시간이 크게 달라진다.
**스텝이 1만 이하인데 수십 시간이 잡히면 VRAM 초과**라는 뜻이니 저사양 전용 판을 쓴다.

> ANIMA 는 IL 때보다 데이터가 많아도 과적합이 심하지 않아 '많많좋'이지만 시간 대비 이득이 적으니 적당히.
> **캐릭터 로라만 구워도 그 작가 그림체는 따라온다.** *(댓글)*

### C·D. 1장 로라 — 그림 한 장으로 그림체 가져오기

C 는 워크플로우, **D 는 그것을 커스텀 노드로 만든 것**이라 D 가 더 편하다.
D 는 로라 로더를 끼우듯 기존 워크플로우 중간에 넣으면 로컬 sd-scripts 를 자동 세팅해 학습하고 적용까지 해 준다.

```text
C  https://drive.google.com/file/d/1zYDMOuQWc5lnbupdoshJ4XPW930wXie3/view
   필요 노드  https://github.com/ShootTheSound/comfyUI-Realtime-Lora
D  https://github.com/goormOwO/comfyui-instant-reference
```

**C 의 사전 준비가 함정이다.** kohya_ss 설치 후 아래를 손으로 복사해야 한다 — **그 경로는 존재하지 않으므로
`venv` 와 `scripts` 폴더를 직접 만들어야 한다.**

```text
.\kohya_ss\venv\Scripts\accelerate.exe
   →  .\kohya_ss\sd-scripts\venv\scripts\accelerate.exe
```

| 항목 | 값 |
|---|---|
| 학습 스텝 / 학습률 | `50` / `0.001` |
| `lora_rank` | `32` |
| `vram_mode`(학습 해상도) | `1024` — ⚠️ **rank 32 를 512 로 학습하면 뭉개진다.** 1024 로 학습할 것 |
| WD14 `threshold` | `0.35~0.5` 가 학습이 가장 잘 됐다 |
| `images_path` | **1장 학습 시 비워 둘 것** (여러 장일 때만 폴더 경로) |
| 소요 시간 | 5090 30초 / 4090 45초 / 3090 80초 / 3060 Ti 120초 |

**결과물 위치** — C 개선판은 `<kohya 경로>/sd-scripts/output` 에 **참조 이미지 · 태그 txt · 로라를 같은 파일명으로** 저장한다.
로라가 쌓였을 때 어떤 이미지로 만든 것인지 바로 확인할 수 있다.

> ⚠️ **한계** — **트리거워드 지정 기능이 없고**, 중간 로라 저장(스텝별)도 지원하지 않는다.
> 여러 장을 학습할 거면 kohya 를 쓰는 편이 낫다.

**쓰는 요령** — 학습에 쓰인 태그를 통째로 적지 말고 **필요 없는 것을 잘라내고 원하는 것만 남긴다.**

```text
학습 태그 전체   1girl, solo, long hair, looking at viewer, bangs, skirt, simple background, ...
실제로 쓸 때     messy hair, black coat, hands in pockets, striped necktie, tanya degurechaff, very long hair,
```

`rem \(re:zero\)` 로 학습한 것을 `tanya degurechaff, monochrome, chibi, sketch, ...` 로 바꿔
**그림체만 가져오는** 것이 이 방식의 핵심 쓸모다.

D 의 오류 둘 — `No module named venv` 는 **0.1.8 이상**으로 올려 해결됐고,
`This MODEL does not expose a recoverable checkpoint path. Load it with a checkpoint loader first.` 는
체크포인트와 이 노드 사이에 다른 노드가 끼어 있을 때 나므로 **0.1.9 이상에서 Train 노드와 Apply 노드를 분리해
Train 노드에 원본 체크포인트를 직접 연결**하면 된다.

> D 는 **바이브 코딩으로 만든 것이라 복잡한 워크플로우에서는 불안정할 수 있다**고 제작자가 밝혔다.
> A 도 제작자가 *"90% 이상 바이브 코딩"* 이라고 적었다.

파이썬 버전 요구사항은 바로 다음 절에 있다. ANIMA 로라가 기존 로라와 왜 호환되지 않는지는
이 문서의 "ANIMA 는 기존 로라가 통째로 안 먹는다" 절과 [ANIMA](anima.md) 를 보라.

## 굽기 I — 윈도우에서는 Python 3.12 여야 한다
<small>2026-03 기준 · 근거 2건</small>

`comfyui-instant-reference`(1장 로라 커스텀 노드) 의 런타임은 **Windows 에서 Python 3.12 가 필요하다.**

```text
RuntimeError: Python 3.12 is required for the instant-reference runtime on Windows.
```

이게 뜨면 3.12 를 설치해야 한다 (실제로 **3.12.10** 을 깔아 해결한 사례).

### 왜 3.13 이 안 되나 — `onnxruntime-gpu` 휠이 없다

```text
error: Distribution `onnxruntime-gpu==1.19.2` ... can't be installed ...
only has wheels with the following Python ABI tags: cp310, cp311, cp312
```

`cp312` 까지만 있고 **`cp313` 이 없다.** 파이썬 3.13 을 쓰는 한 이 노드는 설치 자체가 막힌다.
제작자가 이후 버전에서 **파이썬 버전을 고정하도록 고쳤다.**

| 파이썬 | 결과 |
|---|---|
| **3.12** (예: 3.12.10) | ✅ |
| 3.13 | ❌ `onnxruntime-gpu` 휠 없음 |

> **파이썬 3.13 을 피해야 하는 이유는 여기만이 아니다.** ANIMA 최적화 쪽에서도
> Windows portable Python 3.13 에서 **Triton CUDA 커널 컴파일이 실패**하는 사례가 다수 보고됐다
> (`Failed to find Python libs`, `utils.cp313-winamd64.pyd`).
> **학습·최적화를 같이 할 거면 3.12 로 맞춰 두는 편이 안전하다.**

파이썬 설치와 환경 분리는 [설치와 환경 구성](install.md) 을 보라.

## 굽기 J — 학습이 0~2 스텝에 끝난다면 (본문이 틀린 경우)
<small>⚠️ 2023-02 기준 · 근거 2건 · 자료 엇갈림</small>

**학습을 돌렸는데 진행 표시가 `0 step` 또는 `0~2 step` 에서 멈추고 그냥 끝나 버리는** 증상이 있다.
경로를 잘못 잡았나 싶어 데이터셋 폴더를 몇 번씩 다시 만드는 것이 흔한 반응인데, **거기가 아니다.**

> ⚠️ **원문(69200689) 본문대로 따라가도 이 증상이 나온다. 원인과 해결은 본문이 아니라 댓글에 있다.**

### 원인은 VRAM 부족이다

**해결 — `Settings` → `Training` 에서 이 체크박스를 켠다.**

```text
Move VAE and CLIP to RAM when training if possible. Saves VRAM.
```

**3080 Ti 와 코랩 양쪽에서 정상 진행이 확인됐다.** 그래도 안 되면 **이미지 크기를 줄인다.**

| 증상 | 흔한 오진 | 실제 원인 |
|---|---|---|
| 학습이 0~2 스텝에 끝난다 | 데이터셋 경로가 틀렸다 | **VRAM 부족** |

### 같은 옵션이 옛날에는 다른 이유로 필수였다

2022년 하이퍼네트워크 가이드(원문 60913615)는 **같은 자리의 옵션을 완전히 다른 이유로** 강조했다.

> **VAE 가 적용된 상태로 학습하면 결과가 망가진다.** `unload VAE and CLIP` 옵션을 체크하거나
> VAE 파일 이름을 바꾸고 WebUI 를 재시작해서 VAE 가 개입하지 못하게 해야 하며,
> **수많은 사람이 이것 때문에 학습 시간을 통째로 날렸다.**

즉 이 체크박스는 **① 결과가 망가지는 것을 막고 ② VRAM 을 아껴 학습이 실제로 돌게 한다** — 켤 이유가 둘이다.

*⚠️ 두 원문 모두 **2022~2023년 A1111·SD1.5 시절 하이퍼네트워크 자료**다. 하이퍼네트워크는 지금 LoRA 에
완전히 밀려났으므로 절차 자체를 따라 할 이유는 없다. 살아남는 것은 **"스텝이 안 도는 것은 경로가 아니라 메모리 문제"**
라는 진단 순서와, 학습 중 VAE·CLIP 을 VRAM 에서 내리라는 원칙이다. 요즘 트레이너에서는

## 굽기 K — LoRA / LoCon / LoHa 고르기와 체크포인트 병합
<small>⚠️ 2023-06 기준 · 근거 2건</small>

`LoRA` 라고 뭉뚱그려 부르지만 실제로는 갈래가 여럿이고, **어느 갈래를 고르느냐에 따라 dim/alpha 권장값이 달라진다** (72241015, 2023-03).

### 갈래 셋

| 갈래 | 무엇이 다른가 | 권장 dim / alpha |
|---|---|---|
| **LoRA** | 기본. WebUI 에서 **별도 설치 없이** 쓴다 | `dim 32` / `alpha 16` |
| **LoCon** | **레이어를 더 많이 학습**한다 → **그림체에 유리** | `dim 16` / `alpha 8` / `conv_dim 8` / `conv_alpha 1` |
| **LoHa** | 더 복잡한 캐릭터·그림체를 담을 수 있으나 **시간이 오래 걸린다** | `dim 8` / `alpha 4` / `conv_dim 4` / `conv_alpha 1` |

> **LoCon·LoHa 는 WebUI 에 Lycoris 확장을 설치해야** 일반 LoRA 처럼 쓸 수 있다.
> 셋 다 **낮은 dim 쪽으로 내려간 값**인데, 그 근거는 위 "굽기 D" 의
> *"낮은 dim 에서도 LR 을 올리면 같은 디테일이 나온다"* 와 같다.

### LyCORIS 를 체크포인트에 병합하기

로라를 매번 부르는 대신 **모델에 굽어 넣는** 것이다. 2023년 당시 SuperMerger 같은 GUI 확장이
LyCORIS 를 지원하지 않아 CLI 로만 가능했다 (78304465, 2023-06).

```bash
git clone https://github.com/KohakuBlueleaf/LyCORIS.git
cd LyCORIS
python -m venv venv
.\venv\Scripts\activate.ps1          # 리눅스는  source venv/bin/activate
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu118
```

> **venv 를 쓰는 이유** — 전역에 pip 패키지가 깔리면 나중에 다른 파이썬 코드의 패키지와 꼬인다.
> 이것은 [설치와 환경 구성](install.md) 의 *"kohya 를 WebUI 와 같은 위치에 설치하면 안 된다"* 와 같은 이야기다.
> CUDA 12.x 여도 `cu118` 로 깔아도 된다.

**⚠️ 여기가 함정이다 — 버전을 고정하지 않으면 동작하지 않는다.**

```bash
# requirements.txt 에 버전이 안 적혀 있어 호환성 이슈가 터진다
pip install safetensors==0.2.6 diffusers[torch]==0.10.2 transformers==4.26.0
mv tools/merge.py merge.py
```

```bash
python merge.py ./모델.safetensors ./로라.safetensors ./병합완료모델.safetensors \
  --weight=(평소 쓰던 로라 가중치) --dtype=fp16
```

- 세 번째 인자 경로에 결과가 저장된다. 모델과 로라를 LyCORIS 폴더 안에 미리 넣고 **상대경로**로 쓰는 편이 편하다
- `--dtype=fp16` 은 대부분의 모델이 fp16 이므로 붙이는 것이 권장된다 (용량이 준다)
- ⚠️ **한계** — 여러 개를 병합하려면 `out1.safetensors` 로 저장한 뒤 **그것을 다시 불러 다음 로라를 병합하는 식으로 반복**해야 한다

> **이후 GUI 지원이 추가됐다** *(댓글)* — `kohya_ss` 의 **Utility > LoRA > Merge LyCORIS**.
> 다만 **로라 1개씩만** 되고 비율과 저장 포맷만 조절할 수 있어 위의 한계는 그대로다.

병합이 원본 모델의 성격을 어떻게 깎는지는 [모델 고르기](models.md) 의 "병합의 금기" 항목을 함께 보라.

*⚠️ **시점 주의 (2023)** — LyCORIS 병합 절차의 패키지 버전은 그 시점 기준이다.
지금은 `kohya_ss` GUI 나 ComfyUI 의 병합 노드를 쓰는 편이 낫고, **ANIMA 로라는 이 경로가 통하지 않는다**
(위 "ANIMA 는 기존 로라가 통째로 안 먹는다" 참조). 살아남는 것은 **갈래별 dim/alpha 권장값**과
**여러 로라는 결과를 다시 입력으로 넣어 반복해야 한다**는 구조다.*

## 굽기 L — 파라미터 한 벌 (2025-06, Illustrious 기준) · v-pred 필수 옵션
<small>⚠️ 2025-06 기준 · 근거 2건</small>

위 '굽기 D·E' 가 원리와 용어였다면, 여기는 **2025년 Illustrious 시대에 실제로 로라를 구워 배포한 사람이 공개한 수치 한 벌**이다.
조회 22만이 넘는 웹툰 캐릭터 로라 시리즈의 제작자가 댓글에서 밝힌 것으로, 2023년 값과 달리 **지금 그대로 써 볼 수 있는 값**이다.

| 항목 | 값 | 왜 |
|---|---|---|
| LoRA Base Model | `illustriousXL_v1.1` | |
| **Text Encoder learning rate** | **`0`** | 텍스트 인코더를 건드리지 않아 **기존 태그 이해력을 망가뜨리지 않겠다**는 뜻 |
| **Network Rank** | **`16`** | 한 파일에 캐릭터를 1~2명만 학습하므로 그 이상은 용량 낭비 |
| **Network Alpha** | **`16`** | ⚠️ **Rank 와 무조건 같은 값이어야 한다** |
| **Max Token Length** | **`225`** (기본 75 에서 상향) | 캡션(태그 목록)이 길어 75토큰을 넘기기 때문 |
| **Epoch** | **`6`** | |
| **스텝 — 캐릭터·컨셉** | **`2000~2200`** | |
| **스텝 — 그림체(스타일)** | **`15000~20000`** | |

참고한 가이드는 학습채널의 `https://arca.live/b/hypernetworks/110021224` (포리x 개정판)이고, 거기서 **로라 타입·해상도·Epoch 만 바꿔** 쓴다.

> ⚠️ **제작자가 특히 강조한 것 — `Alpha` 와 `Rank` 는 값이 무조건 같아야 한다.**
> 질문자가 `6` / `8` 로 다르게 줬던 것이 **과적합의 원인**일 수 있다는 맥락에서 나왔다.

이건 위 '굽기 D' 의 *"`alpha/rank` 를 일정하게 고정하고 learning rate 로만 조절한다"* 는 2023년 원리를
**2025년 수치로 특정한 것**이라 서로 어긋나지 않는다.

### ⚠️ v-pred 모델이면 옵션 두 개가 더 필요하다

> **v-pred 기반 모델(NoobAI v-pred 등)에 LoRA 를 학습시키려면
> `v_parameterization` 과 `zero_terminal_snr` 을 반드시 추가해야 한다.**

```text
v_parameterization
zero_terminal_snr
```

**civitai 의 온라인 training 기능은 이 파라미터를 설정할 수 없어서 v-pred 로라를 제대로 만들 수 없다.**
(위 '굽기 B' 의 Civitai 트레이너를 쓰려면 대상이 v-pred 모델이 아닌지 먼저 확인하라.)
그렇다고 **noob eps 모델로 대신 학습하면 결과가 약해진다.** 로컬 kohya_ss / sd-scripts 로 가야 한다.

*(반대 방향의 오류도 알아 두면 좋다 — SD1.x 기반인데 `v_parameterization` 을 켜면
`RuntimeError: Error(s) in loading state_dict for UNet2DConditionModel: size mismatch ...` 가 난다. 위 '굽기 G' 참조.)*

### 배포할 때의 관례 하나

**LoRA Base Model 은 로라를 만들 때 쓴 베이스 모델일 뿐 그림을 만드는 모델이 아니다.**
실제로 그림을 뽑는 것은 Checkpoint Model 이다 — 뉴비가 가장 많이 혼동하는 지점이라 배포자가 본문에 못 박아 뒀다.
동봉된 Metadata(json) 파일명을 LoRA 파일명과 똑같이 맞춰 같은 폴더에 넣으면 **WebUI 에서 트리거워드·프롬프트가 자동으로 뜬다.**

## 굽기 O — ANIMA 스타일 로라 전 과정 (2026-06, anima_lora)

### 태깅 — taggui

```text

2) Ctrl+A 로 전체 선택 → add tag 로 트리거 워드 일괄 입력
3) auto-captioner 에서 모델을 SmilingWolf/wd-swinv2-tagger-v3 로 선택
4) start auto-captioning
※ 토큰 초과 경고가 빨갛게 떠도 무시 — ANIMA 는 512 토큰까지 지원한다
```

**그림체 로라는 보이는 것을 전부 태깅**하는 편이 좋고, **캐릭터 로라는 반대로** 머리색·눈색 같은
고유 특징 태그를 지워야 그 특징이 트리거에 녹아든다.

### 학습량 — 스텝은 곱셈으로 정해진다

```text
스텝 수 = 데이터셋 장수 × max train epochs

스타일 로라   2000 ~ 3000 스텝     (400장 × epochs 6 ≒ 2400 스텝)
캐릭터 로라   2500 스텝 언저리      (댓글: 15~30장 단독 인물. 4000 까지는 필요 없다)
```

설정은 Method `lora` / 변형 `lora`, network alpha·dim 은 기본값 유지(`32/64` 나 `64/64` 도 가능),
path scope 에 데이터셋 경로, output name 에 로라 이름을 넣는다.
`checkpointing epochs` 는 최종본만 볼 거면 `max train epochs` 와 같은 값으로 둔다.

### 속도와 결과물

```text
5070 Ti  2500~3000 스텝  →  40~50분  (스텝당 0.77초)
결과물   output\ckpt\로라명.safetensors  → 로라 폴더로 복사
```

## 굽기 P — 학습 자료가 아예 없는 대상 (합성 데이터 루프 · 3D 스크린샷)

danbooru 에도 픽시브에도 자료가 없는 대상은 데이터를 **만들어서** 학습시킨다. 두 갈래가 있다.

### 갈래 1 — 1차 로라로 데이터를 불려 나가는 루프

hanged(고어) 로라 배포자가 쓴 방법이다.

```text
1) 픽시브·danbooru 에서 이미지를 대충 모은다
2) 그것으로 LoRA 를 학습시킨다

6) 다시 괜찮은 것만 정제한다
7) 다시 학습한다
```

### ⚠️ 이 방법은 "AI 그림으로 학습하지 마라" 와 정면으로 부딪힌다 — 양쪽 다 적는다

| 쪽 | 무엇이 확인됐나 |
|---|---|
| **하지 마라** | 공식 일러가 2장뿐인 캐릭터를 나노 바나나로 40장 뽑아 학습했더니 포니테일·생머리 같은 특징은 잡혔으나 **눈동자가 뭉개지고 리본이 엉켰다.** 웹툰 로라 제작자도 **사람 눈에 안 보이는 노이즈** 탓에 앞머리 선이 파랗게 칠해지고 색감이 과해졌다고 보고했다. AI 이미지로 학습한 계곡주 로라는 눕는 프롬프트를 안 넣었는데도 **눕는 그림이 많이 나왔다** |
| **된다** | 위의 반복 루프로 만든 hanged 로라는 실제로 배포됐다 |

**갈림은 "뽑은 것을 그대로 넣느냐, 매 회차 사람이 선별·인페인트로 걸러 내느냐" 에 있다.**
실패 사례들은 뽑은 것을 그대로 넣은 쪽이고, 루프 쪽은 매 단계에 수동 선별이 들어 있다.
**정말 어지간히 마이너한 대상이 아니면 사람이 그린 그림으로 학습시키는 편이 낫다.**

### 갈래 2 — 3D 스크린샷으로 2D 캐릭터 굽기 (코이카츠)

**적용 범위부터 확인한다** — 이 방법은 **자작 캐릭터처럼 세상에 그림 자료가 없는 대상용**이다.
이미 존재하는 캐릭터인데 모델이 다르게 그리는 것이라면 **팬아트를 긁어 학습시키는 편이 훨씬 쉽고 좋다**고
작성자가 못 박았다.

핵심은 **캐릭터와 그림체를 태깅으로 분리**하는 것이다.

```text
캡션 맨 앞    och                        ← 새 토큰. 캐릭터 특징 태그(animal ears, blue hair,
                                            cat ears, ahoge …)를 전부 지워 이 안으로 흡수시킨다
바로 뒤       3D game koikatsu (medium)  ← 그림체를 여기로 따로 떼어 낸다
의상          och room wear              ← 묶어서 태깅
```

정규화 이미지 700장을 별도 reg 폴더가 아니라 `img` 아래에 나눠 한꺼번에 학습시켰다.

```text
img/1_iom person/   정규화 700장 × 1반복
img/3_iom person/   스크린샷 216장 × 3반복
학습 옵션           v_param  +  --zero_terminal_snr   (v-pred 모델 학습)
VRAM                12GB 로 다른 작업을 못 할 만큼 빠듯
```

뽑을 때는 `(원하는 작가:0.6)` 을 지정하고 **네거티브에 `(3D game koikatsu \(medium\):0.6)`** 을 넣어
3D 화풍이 새는 것을 막는다.

> **촬영 함정** — 코이카츠 스크린샷은 **1초 안에 두 번 찍으면 한 장만 남는다.**
> 한 장당 **1.4초** 간격이 안전하고, 매크로는 키마다 **700ms** 딜레이면 충분하다.

## 굽기 R — 다 구운 뒤 — 용량 줄이기와 파일 종류 판별
<small>⚠️ 2023-04 기준 · 근거 3건</small>

### 용량 줄이기 (resize)

kohya sd-scripts 의 `networks/resize_lora.py` 로 이미 구운 로라의 랭크를 낮춰 용량을 줄인다.

```bash
python networks/resize_lora.py \
  --save_precision=fp16 \
  --new_rank=64 \
  --dynamic_method=sv_ratio \
  --dynamic_param=5 \
  --model=원본.safetensors --save_to=결과.safetensors
```

| 인자 | 권장 범위 |
|---|---|
| `--new_rank` | 기본 64 |
| `--dynamic_method` | `sv_ratio` / `sv_cumulative` / `sv_fro` |
| `--dynamic_param` | sv_ratio **2 이상**, sv_cumulative·sv_fro **0~1** |

**값에 따라 결과가 크게 달라진다.**

```text
원본 64MB  →  sv_fro 0.99   44MB
           →  sv_ratio 5    19MB
           →  sv_ratio 18   52MB
```

무조건 작게 만드는 것이 아니라 **원본과 차이가 안 나는 지점을 직접 뽑아 찾아야 한다**(본문 모델은
sv_ratio 5 이상부터 원본과 비슷해졌다). 코랩에서 `FileNotFoundError` 가 나면 구글 드라이브를 먼저 마운트한다.

### 받은 파일이 LoRA 인가 LoCon 인가 LoHa 인가

블록으로 판별한다.

| 조건 | 종류 |
|---|---|
| 블록 개수 **264개** | LoRA |
| 블록 이름에 **`conv`** | LyCORIS / **LoCon** |
| 블록 이름에 **`hada`** (또는 판별 중 `nan`) | LyCORIS / **LoHa** |

판별 스크립트는 `dimension`(네트워크 차원)과 `alpha` 도 함께 보여 주고, 값이 하나로 통일돼 있지 않으면
Dynamic 으로 평균·표준편차·개수를 낸다. 로컬에 torch 가 없으면 **WebUI 의 venv 안에서 실행**하면 된다.

> LoHa 가 LoRA 보다 품질이 좋으냐는 질문에 배포자의 답은 **"취향 차이"** 였다 — 방식 자체가 우열을 가르지 않는다.

## ⚠ 태그 정제 — 중복 통합은 이득인가 색 오염인가 (본문과 댓글이 갈린다)
<small>⚠️ 2023-05 기준 · 근거 1건 · 자료 엇갈림</small>

캐릭터 LoRA 태깅에서 **본문과 댓글이 정면으로 갈린 지점**이다. 양쪽 다 실제 경험이라 둘 다 적는다 (77256966, 2023-05).

### 본문 — 중복 태그를 하나로 통합하면 적은 데이터로도 학습이 잘 된다

30장짜리 캐릭터 로라를 두 번 만들어 비교한 기록이다.

| 시도 | 태깅 | 결과 |
|---|---|---|
| 1차 | 오토 태깅 후 **트리거와 `1girl`, `solo` 정도만** 지우고 학습 | **잘 먹히지 않았다.** 의상 구현도가 떨어지고 타율도 나빴다 |
| 2차 | **중복 태그를 하나로 통합** (`skirt` / `plaid skirt` / `yellow skirt` **→ `yellow plaid skirt`**) + **표정·배경 태그 제거** | **적은 데이터로도 학습이 훨씬 잘 됐다** |

> 정제해도 차이가 없다면 **데이터셋 자체가 문제**일 수 있다는 것이 작성자 의견이다.

### 댓글 — 그 방식은 색 오염을 부른다

> **중복 태그 통합은 색 오염이 자주 생겨서 흰 스타킹이 검은 스타킹으로 바뀌는 경우가 많다.**
> **옷 갈아입히기를 포기할 거라면 태그를 트리거 하나로 몰아 넣는 '1토큰 태깅' 도 좋다.**

### 어떻게 놓을 것인가

**목적에 따라 갈리는 문제로 보는 것이 맞다.**

| 목적 | 방향 |
|---|---|
| **적은 데이터로 캐릭터를 확실히 뽑는 것**이 목적 | 중복 통합 + 표정·배경 태그 제거 (본문) |
| **다른 옷을 입히는 것**이 목적 | 통합에 신중. 색 오염 위험 (댓글) |
| **옷 갈아입히기를 아예 포기** | **1토큰 태깅** (댓글) |

### 정제하지 않았을 때 실제로 일어난 일

본문 로라는 **의상 태그를 정제하지 않고 학습시켰고**, 그 결과가 이렇다.

- 다른 옷으로 **갈아입히는 게 잘 안 된다**
- **상의가 계속 노란색으로 고정**된다
- **리본이 떨어지지 않는다**
- 길쭉한 그림체를 원해 `chibi` 를 네거티브에 넣으면 되긴 하지만 **가끔 씹는다**

> 이 문제의 반대편에 있는 규칙이 위 항목들에 있다 — **캐릭터의 신체·고유 특징 태그는 캡션에서 지워야** 캐릭터의 일부로 흡수되고, **의상 태그는 지우지 않아야** 다른 옷을 입힐 수 있다.
> 즉 '지우기' 와 '통합하기' 는 다른 조작이고, **통합의 부작용이 색 오염**이라는 것이 이 글의 기여다.

```text
1. 프롬프트에 트리거 워드와 <lora:이름000001:0.1> 을 넣어 둔다
   (파일명의 에포크 구분 번호와 시작 weight 를 기준으로 잡는다)

2. x/y/z plot 스크립트에서 x축·y축을 모두 '프롬프트 스타일 변경(Prompt S/R)' 으로 고른다

   x축   LoRA weight     0.1, 0.2, 0.3 ... 1.0
   y축   에포크 번호      000001, 000002, 000003 ...
   z축   시드            아무 값이나 여러 개 (다양한 상황에서 보기 위해)

3. 체크박스는 '범례 그리기' 만 켜고 Grid margins 는 1~4
```

그러면 **에포크 × weight 격자 비교표**가 나온다.

> **댓글 보강 — weight 를 0.1 단위로 다 뽑을 필요 없다. 0.2 단위로 체크해도 판단에 충분하고 생성량이 절반으로 준다.**

로라의 **블록별** 최적값을 같은 방식으로 훑는 것은 위 「로라가 프롬프트를 잡아먹을 때」 절의 XYZ 제약을 함께 볼 것.

## 곁가지 — 색상 임베딩: 스텝보다 '초기화 텍스트' 가 결정한다 (2022-12)
<small>⚠️ 2022-12 기준 · 근거 1건</small>

LoRA 는 아니지만 **'무엇을 학습시킬 수 있는가' 의 감각을 넓혀 주는 사례**다 (1건, 2022-12, SD1.5).

AI 는 `#RRGGBB` 같은 색상 코드를 읽지 못한다. 그런데 임베딩(Textual Inversion)이 프롬프트처럼 쓰인다는 점을 이용하면
**특정 색상 자체를 임베딩으로 학습시켜 색 지정 태그를 만들 수 있다.**

```text
사용      : 1girl, skyblue01-30 hair      ← 일반 blue hair 와 확연히 다른 지정 색이 나온다
```

### ⚠ 스텝 수보다 '초기화 텍스트' 가 결정적이다

작성자가 나중에 덧붙인 가장 중요한 주의사항이다.

> **학습 시작 시 '초기화 텍스트(initialization text)' 에 넣은 색상에 결과가 아주 크게 좌우된다.**
> 기본값인 `*` 를 그대로 두면 **스텝을 아무리 높여도 원하는 색이 나오지 않고**,
> `pink` 같은 색을 넣으면 스텝이 돌아가며 원하는 색으로 수렴하다가 다시 엉뚱한 곳으로 가 버린다.

이 부분은 연구가 더 필요하다고 남긴 채 끝났다. 당시 Anything 3.0 순정이 `amber`·`tawny` 같은 색 태그를 잘 못 알아들어 대안이 됐다.

> **일반화되는 것** — 학습에서 **초기값(어디서 출발하느냐)이 학습량보다 결과를 크게 가르는 경우가 있다.**
> 위 「굽기 준비 ①  무엇을 베이스로 구울 것인가」 와 같은 종류의 문제다.

## LoRA 말고 다른 파인튜닝 — sDCTFT · D-OPSD, 그리고 krea2 로라 + 레퍼런스
<small>2026-07 기준 · 근거 3건</small>

LoRA 말고도 **적은 파라미터만 건드려 파인튜닝하는 방식**들이 채널에 소개된 적이 있다. 둘 다 코드가 공개돼 있다.

### sDCTFT — 주파수 계수 몇 개만 학습한다 (2026-02)

```text
구현 https://github.com/bemoregt/Train_sDCTFT_FineTuning_using_SDXLModel.git
논문 arXiv:2410.09103  (MaCP / sDCTFT)
```

가중치 행렬에 **2D DCT(이산 코사인 변환)** 를 걸어 주파수 영역으로 옮긴 뒤 **일부 계수만 학습**한다.
LoRA 가 저랭크 행렬을 덧붙이는 것과 달리 이쪽은 주파수 계수 몇 개만 건드린다.

| 항목 | 값 |
|---|---|
| 학습 파라미터 | SDXL UNet **2.57B 중 84,560개 (0.003%)** |
| 선택 방식 | 주파수 거리 `d(u,v)=√(u²+v²)` 기준 3개 밴드 → 각 밴드에서 에너지 상위 70% + 랜덤 30% |
| 순전파 | ΔW 를 실체화하지 않고 2단계로 계산 |
| **출력** | 학습 후 **SVD 로 압축해 kohya 호환 LoRA safetensors** 로 저장 → **ComfyUI 에서 바로 쓸 수 있다** |
| 실행 | `images/` 폴더에 이미지를 넣고 `python finetune_sdctft.py` (SDXL 베이스는 최초 1회 자동 다운로드) |

댓글에 따르면 **맥미니 16GB 에서도 파인튜닝이 돌아간다.**

### D-OPSD — 증류 모델을 파인튜닝할 때 (2026-05)

증류(distill)된 few-step 모델을 **기존 방식(이미지+캡션에 노이즈만 넣어 학습)으로 파인튜닝하면
새 개념·스타일은 학습되지만 실제 생성 결과가 흐릿하거나 이상하게 나온다.** 그 문제를 푸는 기법이다.

```text
학생  태깅 텍스트만 보고 평소 추론하듯 저스텝 샘플링을 굴려 자기 중간 경로를 만든다
선생  텍스트 + 이미지를 함께 본 상태로 그 경로의 각 지점에서 가야 할 방향(velocity)을 예측한다
      → 학생은 자기 방향을 선생과 일치시키도록 자기만 업데이트, 선생은 EMA 로 천천히 따라온다
추론  학습이 끝나면 선생 분기(텍스트+이미지 경로)는 버리고 원래의 텍스트 전용 파이프라인을 그대로 쓴다
```

하나의 모델이 학생과 선생을 겸할 수 있는 것은 **요즘 모델이 VLM/LLM 을 텍스트 인코더로 쓰기 때문**이다.
결과적으로 few-step 추론 능력을 유지하면서 이미지를 과적합하지 않고, 적은 데이터셋으로 LoRA 를 학습해도 미학습 프롬프트로 일반화된다
(`https://github.com/vvvvvjdy/D-OPSD` — 학습 코드는 추후 공개 예정).

> ⚠️ **댓글의 전제 하나가 틀렸다.** 'ANIMA 가 T5 를 버리면 적용 가능할지도' 라는 기대가 나왔는데,
> **Z-Image 도 ANIMA 도 애초에 T5 를 쓰지 않는다.** ANIMA 는 **Qwen3 중간에 어댑터를 끼우는 구조**이고
> D-OPSD 는 비전 모델도 필요해 보여 적용이 쉽지 않다는 것이 결론이었다.

### krea2 에서 캐릭터 로라 + 이미지 레퍼런스 (2026-07)

### 결과는 단조롭게 개선되지 않는다

> 로라 학습에 막 입문해 **세팅도 제대로 못 잡고 만든 초기 로라가 이후 한동안 개선판들보다 성능이 좋았다.**
> 데이터셋을 개선하고 꾸준히 만진 뒤에야 겨우 따라잡거나 추월했다. *"나만 그런 게 아니다, 내 최장 기록은 쓰레기 스무 개였다"*

## 굽기 보론 — 데이터셋을 무엇으로 채우나 (프롬프트 출력 · 태거 threshold · 흑백 변환)

데이터셋을 무엇으로 채울 것인가에 대해 2026-07 의 두 글이 서로 다른 답을 준다.

### ⚠ 프롬프트로 뽑은 출력으로 학습하면 원본에 닿을 수 없다

마이너 캐릭터의 외모와 의상을 나눠 학습시키려고 **의상 프롬프트만으로 데이터셋을 뽑으려던** 시도가 있었다 —
포즈·배경 와일드카드에 의상 프롬을 넣고 200장을 뽑아 그중 통일된 30장을 쓰는 계획이었다.

> **댓글의 반론이 핵심이다** — *프롬프트만으로 뽑은 출력에 만족한다면 애초에 학습할 의미가 있느냐.
> 그런 데이터로 학습하면 원본에 **근접할지는 몰라도 닿을 수는 없다.***

대신 권해진 것은 **원본을 태거(`taggui`)에 돌려 나온 태그를 그대로 프롬프트로 쓰고
threshold(값이 낮으면 더 많은 단어가 태그된다)를 조절하는 것**이다. 태거 모델별 차이는 크지 않다.

**결말이 답이다** — 원본 유효 이미지가 3장뿐이라 100% 재현은 포기하고,
**인페인팅을 적극적으로 써서 핵심 데이터셋 50장을 만들어** 학습해 만족했다 → [인페인팅·아웃페인팅](inpainting.md).

> 참고로 그 글에서 타율이 가장 높았던 의상 프롬프트는 **같은 부위를 두세 개의 유의어 태그로 겹쳐 누르는** 방식이었다
> (`white crop top, sleeveless crop top` / `elbow-length leather gloves, brown leather gloves`).
> 다만 [프롬프트 쓰는 법](prompting.md) 에는 **동의어를 여러 개 쌓으면 오히려 나빠진다**는 반대 방향의 관찰이 있다 —
> **겹치더라도 단부루에 실재하는 태그끼리만** 겹쳐야 한다. (원문 프롬프트에는 쉼표가 두 군데 빠져 있다.)

**AI 가 흑백을 잘못 구분하는 경우가 있어** 회색 부분을 피부색에 가깝게 변환해서 학습 데이터로 썼다는 가공 요령이다 (1건, 2026-07).

## 굽기 보론 — 단면도(`cross-section`)는 학습으로도 잘 안 된다
