# NovelAI (NAI)

> **원문 104건 → 이 문서 하나** · 주장 205개 · 정리 2026-08-14

**설치 없이 결제만 하면 되는 길이다.** 그래픽카드가 없거나 AMD 라데온·인텔 Arc 라면 채널의 표준 답이 여기다.
로컬(ComfyUI·Forge Neo)과는 요금 구조도 프롬프트 문법도 다르다 — 그 차이를 이 문서에 모았다.
전체 지도는 [처음이라면](overview.md), 낱말은 [용어집](glossary.md).

## 1. NAI 를 쓰는 이유 — 로컬과 뭐가 다른가
<small>⚠️ 2024-06 기준 · 근거 3건</small>

NovelAI 는 **애니 스타일 모델을 최초로 서비스한 회사**이자 그 웹서비스다. 2022년 10월 그 모델이 유출돼 시중에 풀린 것이 지금 로컬 생태계의 출발점이다(해커가 아니라 함께 연구하던 쪽이 공개했다는 반론도 댓글에 있다).

| | NAI (웹) | 로컬 (ComfyUI · Forge Neo) |
|---|---|---|
| 그래픽카드 | **필요 없다** | NVIDIA 필요 |
| 시작까지 | 결제하고 바로 | 파이썬·git 설치 → 클론 → 모델 다운로드 |
| 돈 | Opus 월 3만원대, 또는 Anlas 충전 | 전기값 |
| 모델 | NAI 가 정한 것만 | 아무거나. 로라·컨트롤넷·확장 자유 |
| 막혔을 때 | 서비스 안에서 해결 | 채널에 물어볼 수 있다 |

**AMD Radeon·Intel Arc 사용자는 NAI Opus 구독이 권장된다.** 원문 109424774 는 "되기는 하지만 사용자가 적어 문제가 생겨도 답을 못 얻으니 이런 카드면 Opus 를 권한다"고 적었다. GTX 1060 3GB·RTX 2050 노트북도 마찬가지로, 그 고생과 전기값을 생각하면 Opus 가 낫다는 것이다.

## 2. 2026-07 API 이전과 Persistent API Token — 400 오류의 첫 용의자
<small>2026-07 기준 · 근거 6건</small>

**2026년 7월 이후 NAI 서드파티 도구가 400 을 뱉으면 이것부터 의심하라.** 두 가지가 한꺼번에 바뀌었다.

### ① 서버 주소가 옮겨졌다

```text
api.novelai.net   →   image.novelai.net
```

`GET /user/information` · `GET /user/subscription` · `POST /user/login` 이 **전부** 새 주소다.
구 서버의 `POST /user/login` 은 이제 **HTTP 400 만 반환**한다 *(2026-07-04 확인)*.

이 하나 때문에 **API 키 로그인 실패 · ID/PW 로그인 실패 · ANLAS 조회 실패가 한꺼번에** 났다.
NAIA 는 다음 두 파일의 주소만 바꿔 임시로 고쳤다 — 고칠 곳이 정말 그것뿐이었다.

```text
resources/naia-backend/core/api_verification.py
resources/naia-backend/core/api_service.py

    https://api.novelai.net/user/subscription
 →  https://image.novelai.net/user/subscription
```

**이 오류 메시지가 뜨면 확정이다.**

```text
ANLAS remaining fetch failed: 400
{"statusCode":400,"message":"Please refresh NovelAI.net. If using a third-party tool, update to the image URL."}
```

NAIApp 제작자도 처음엔 **로그인 URL 만 바뀐 줄 알았다가** 추가 패치로 나머지를 마저 고쳤다.
NAI Helper 는 v1.2.3 에서 *'api token 을 입력하니 연결 테스트 실패 400'* 을 같은 이유로 잡았다.
지금은 NAIA · NAI-Auto-Generator · NAIApp · NAI Helper 모두 정식 업데이트로 해결됐으니,
**쓰는 도구를 최신판으로 올리는 것이 첫 번째 답**이다. 직접 만든 도구라면 엔드포인트를 바꿔라.

### ② 로그인은 이제 Persistent API Token 뿐이다

NovelAI 기존 로그인 API 에 **reCAPTCHA 인증이 붙었다.** 그래서 서드파티 앱이 이메일·비밀번호로
로그인하는 방식은 더 이상 안정적으로 쓸 수 없고, NovelAI 도 사용자 대상 서드파티 앱은
`Persistent API Token` 을 쓰라고 권고했다. 재로그인이 `please refresh novelai.net` 으로 실패하는
증상이 그것이다.

> [자원](resources.md) 문서에는 "비공식 클라이언트는 reCAPTCHA 로 로그인 불가" 라고만 적혀 있는데,
> **막힌 것이 아니라 길이 바뀐 것이다.** 토큰을 쓰면 지금도 된다.

| 단계 | 위치 |
|---|---|
| 1 | NovelAI 웹사이트 로그인 |
| 2 | 좌측 상단 **설정(톱니바퀴)** → `Account` |
| 3 | `Get Persistent API Token` 으로 토큰 생성 후 복사 |
| 4 | 앱 로그인 화면의 **API 키** 칸에 붙여넣기 |

토큰은 `pst-` 로 시작한다.

> ⚠️ **Overwrite 로 새 토큰을 발급하면 기존 토큰이 무효화된다.**
> 여러 앱에서 같은 토큰을 쓰고 있었다면 **전부 새 토큰으로 다시 등록**해야 한다.

NAI-Auto-Generator V4.5 는 로그인 대화상자에 `API 키` 탭을 넣었고, NAIApp 은 v1.5.1 에서
Persistent API Token 전용으로 바꿨다. 앱 안의 *'Persistent Token 발급 방법 보기'* 에서도 절차를 볼 수 있다.

그래도 안 되면 [오류 해결](troubleshooting.md) 을 보라.

## 4. 기본 설정 (2023-11 · V3 시절)
<small>⚠️ 2023-11 기준 · 근거 2건</small>

**이 항목은 시점이 낡았다.** 원문 작성자 본인이 첫머리에 *"아래 문법 중 대다수가 실제 사실과 상이하니 참고용으로만 쓰고, V4 출시 기점으로 재작성 예정"* 이라고 붙여 두었다. 지금은 V4.5 이후라 세부 설정이 다르다. 그래도 **어떤 항목을 만지는 화면인지**는 그대로다.

| 항목 | 당시 권장 |
|---|---|
| Add Quality Tags | **off** |
| Undesired Content Preset | Heavy → **None** |
| Sampler | Euler → **DPM++ SDE** |
| SMEA | **ON** |
| DYN | **ON** |

**Undesired Content(UC)** 는 WebUI 의 네거티브 프롬프트에 해당하는 칸이다. 당시 붙여 넣던 문자열:

```
normal quality, bad quality, low quality, worst quality, lowres, displeasing, very displeasing,
{bad}, bad anatomy, bad hands, text, error, missing, missing finger, extra, extra digits, fewer,
fewer digits, cropped, JPEG artifacts, signature, watermark, username, blurry, artist name,
bad face, fat, duplicate, mutation, deformed, disfigured, extra arms, extra legs, long neck,
bad feet, bad proportions, unfinished, chromatic aberration, scan, scan artifacts
```

UC 는 '지우고 싶은 것'을 넣는 데도 쓴다 — 배경·옷을 없애고 싶으면 프롬프트에서 빼는 대신 UC 에 `outdoor, jacket, shirt, skirt, necktie, socks` 를 넣는 방식이다.

### 같은 시절의 실사용 한 벌 (2023-11, V3)

위 표가 '무엇을 만지나' 라면 이건 실제로 쓰인 값이다. 월페이퍼 출품작 하나에서 왔다.

```text
Size 1856x1280 / Steps 28 / Guidance 5 / Sampler Euler (auto 옵션 켬)
Add Quality Tag         켬        ← 위 표의 당시 권장(off)과 반대다. 사람마다 갈렸다
Undesired Content Preset Heavy    ← 그 위에 직접 쓴 네거티브를 더한다
```

- 중괄호 `{ }` 는 이 시절 NAI 의 강조 문법으로 **한 겹당 약 1.05배**다(A1111 의 소괄호에 대응).
- **NAI 의 `Steps`/`Guidance` 는 A1111 의 CFG 와 이름도 범위도 다르므로 값을 그대로 옮기면 안 된다.**
  Guidance 5 는 A1111 의 CFG 5 와 같은 뜻이 아니다.
- 작성자가 밝힌 의도는 *"부정 프롬프트에서 손가락 조지는 것을 앞에 뒀다"* — **네거티브에도 순서가 영향을 준다**고 보고
  중요한 것을 앞에 배치한 것이다.

> ⚠ 다만 그 네거티브에 든 `more than two arm per body` · `more than two leg per body` ·
> `more than five fingers on one hand` · `hair crosses the screen border` 는 **전부 단부루 태그가 아니다.**
> 손가락·팔다리 수를 영어 문장으로 비는 이 시절의 관용구이고 근거가 없다
> → [프롬프트 쓰는 법](prompting.md) 「⚠ 폐기·오작동 태그와 즉석 조합」.

## 5. 프롬프트 문법 — 로컬과 다른 점
<small>2026-07 기준 · 근거 9건 · 자료 엇갈림</small>

**가중치 문법이 A1111 계열과 다르다. 그리고 공백 한 칸이 문법의 일부다.**

| 계열 | 표기 | 예 |
|---|---|---|
| A1111 / ComfyUI | `(태그:1.2)` | 괄호 한 겹당 1.1배 — `(((검은머리)))` = 1.331배 |
| **NovelAI** | `weight::tag ::` | `1.2::blue eyes ::` · 음수도 된다 — `-1::tears, bags under eyes ::` |

> ⚠️ **닫는 `::` 앞의 공백이 필수다.**
>
> ```text
>  맞다 :  1.2::blue eyes ::
> 틀리다:  1.2::blue eyes::
> ```
>
> 프롬프트 지시문을 정리한 두 글(원문 162982020 · 164361100)이 **`tag::` 는 틀리고 `tag ::` 가 맞다**고 못박는다.
> 다만 채널에 도는 예시 프롬프트에는 `2::태그::` 처럼 **공백을 뺀 표기가 섞여 있다**(원문 162601951 · 175610298).
> 가중치가 안 먹는 느낌이면 **공백부터 확인하라.**

`{}` · `[]` 강조는 **V3 레거시**다. V4/V4.5 공식 문법은 `::` 방식이다.
작가를 두 명 이상 쓸 때 붙이는 `-3::artist collaboration ::` 를 비롯한 나머지 규칙은 다음 절에 있다.

**태그 순서를 지켜야 한다.** 맨 앞 줄과 맨 끝 줄의 위치는 반드시 지키고 중간 태그의 순서는 섞여도 무방하다. NAI 가 그런 순서를 전제로 학습됐고 퀄리티 태그도 기본값이 맨 끝에 붙게 돼 있기 때문이다 (2023-11 V3 기준).

```
1girl, <캐릭터 이름>, <작품(단부루 copyright 태그)>, <artist:작가이름>,
  컷 / 포즈 / 얼굴 / 머리 / 신체 / 옷 / 배경 ...
best quality, amazing quality, very aesthetic, highres, incredibly absurdres
```

NAI 가 **공식으로 권장하는 순서**는 이렇게 정리돼 있다 (2026-07):
`dataset → 인원 → 캐릭터/시리즈 → 품질·화풍 → 외형 → 포즈·표정 → 구도 → 배경 → 디테일`

**그 밖에**
- 작가 태그는 단부루에 등록된 이름 그대로, **괄호까지 포함**해 쓴다 — `artist:ryota (ry o ta)`
- 장르(작품) 태그만 넣어도 그 게임의 화풍·분위기를 따라간다
- 기존 캐릭터의 옷·머리·가슴을 바꿀 때는 `alternate costume` / `alternate hairstyle` / `alternate breast size` 를 **최상단**에 넣으면 원본 디자인이 덜 끌려온다
- 체형·나이는 `curvy` · `loli` · `hourglass` · `slender` 묶음에 `::` 가중치를 붙여 지정하고, 작가 태그는 0.1~0.65 같은 **낮은 가중치로 여러 명을 섞는** 것이 관례다
- 태그는 지어내지 말고 danbooru.donmai.us 에서 실제로 있는지 확인한다. 게시물 수 **500 미만**이면 재현율이 낮아 대체 태그를 찾는 편이 낫다

## 6. 프롬프트 규칙집 — 도메인 분리 · 태그 순서 · 충돌 태그
<small>2026-03 기준 · 근거 2건</small>

LLM 에게 프롬프트를 짜게 시킬 때 쓰는 대형 지시문 두 판이 공개돼 있는데(2026-02 · 2026-03),
그 안에 담긴 규칙 자체가 **NAI 프롬프트 국룰의 집약**이라 사람이 직접 쓸 때도 그대로 통한다.

### 도메인은 절대 섞지 않는다

| 도메인 | 담는 것 |
|---|---|
| **Base** | 인원수 · 구도 · 앵글 · 장소 · 작가 · 연도 · 소스 · 스타일 · 퀄리티 |
| **Character** | 성별 · 캐릭터명 · 시선 · 역할 · 상황 · 포즈 · 행동 · 표정 · 머리 · 몸 · 의상 · 액세서리 · 신발 |

### 태그 순서

```text
Base (NAI) :  Count > Comp > Artist > Year > Source > Style > Quality
Base (로컬):  Source > Style > Artist > Year > Count > Comp > Quality
캐릭터      :  Gender > Char/Gaze > Role/Sit > Pose/Act > Face/Expr > Hair > Body > Outfit > Acc > Shoes
```

**Quality 는 항상 마지막이다.** 캐릭터 쪽을 15단계로 더 쪼갠 판도 있다 —
`01 gender / 02 character / 03 gaze / 04 job·race / 05 situation / 06 pose / 07 action /
08 expression / 09 얼굴 디테일+만푸 / 10 hair / 11 body / 12 body state / 13 outfit /
14 accessories(머리→발) / 15 shoes`.
뿔·날개·꼬리는 **신체 부위면 11, 장식이면 14** 로 간다.

### 작가를 두 명 이상 쓸 때 — `-3::artist collaboration ::` 는 필수다

```text
artist:aaa, 0.85::artist:bbb ::, 0.65::artist:ccc ::, -3::artist collaboration ::
```

작가 태그를 나열했으면 **맨 뒤에 반드시 붙인다.** 두 판이 모두 '필수'라고 적었다.
실사용 예시에서는 `-0.5` 나 `-1` 로 쓰기도 한다.

### 음수 가중치 (NAI 에서만 된다)

| 목적 | 표기 |
|---|---|
| 제거 | `-1::hat ::` |
| 반전 — 색상 추가 | `-1::monochrome ::` |
| 디테일 추가 | `-3::simple illustration ::` |

닫는 `::` 앞의 **공백**을 다시 확인하라 → 위 「프롬프트 문법」 절.

### 서로 잡아먹는 태그 조합

| 조합 | 왜 |
|---|---|
| `cowboy shot` + `shoes` | cowboy shot 은 **허벅지에서 잘리므로** 신발이 안 보인다 |
| `mechanical hands` vs `mechanical hand` | 복수/단수가 다른 태그다 |
| `grabbing another's breast` vs `grabbing own breast` | 잡는 대상이 다르다 |
| `from behind` + `back` | 중복 |
| `looking back` + `back` | 동작과 상태가 섞여 충돌 |

### 캐릭터 2인 이상

- NAI 는 `[Base]` / `[Char1]` / `[Char2]` 로 **섹션을 분리**한다 (로컬은 단일 `[Merged]` 에 `BREAK`)
- **공유 동작도 캐릭터별로 따로 할당한다.** `[Character공유]` · `[Pose]` · `[Background]` 같은 헤더 공유는 금지
- 같은 `kissing` 이라도 한쪽은 `on top, leaning over`, 다른 쪽은 `leaning back, head back` 처럼 포즈를 다르게 쓴다

### 태그 CSV 를 LLM 에 통째로 물리는 것에는 반박이 있다

> 이 지시문에 딸린 태그 CSV 를 그대로 올려 쓰라는 안내에 **댓글이 반박했다** — CSV 가 AI 의 컨텍스트를
> 현저히 초과해서(제미나이 기준 **340만 토큰**) 앞 2000줄 정도만 읽고 답을 뱉으므로 개소리가 나올 확률이 높다는 것이다.
> **작성자도 이 지적을 받아들였다.**
> 제대로 된 해법은 **AI 가 태그를 먼저 만들게 한 뒤 코드 실행으로 태그 사전을 `grep` 해 실제 존재 여부를
> 검증하고 잘못된 태그를 교체**하게 구성하는 것이다. 그러면 전체 파일을 읽을 필요가 없다.

## ⭐ `source#` · `target#` · `mutual#` — 하는 쪽 · 당하는 쪽 · 상호작용을 태그 단위로 나눈다 (V4)
<small>⚠️ 2025-03 기준 · 근거 2건</small>

NAI V4 에서 가장 크게 달라진 것은 **다인물 상호작용을 태그 단위로 쪼개 캐릭터마다 따로 배정할 수 있게 된 것**이다.
V3 에서 0.5% 도 안 나오던 후타×남 삽입 구도가 **30~50%** 로 올라왔다는 것이 실사용 체감이고,
V3 에서 팔 3개짜리 키메라가 나오던 '여캐 둘이 남캐 하나를 껴안는' 구도도 이 문법으로 높은 확률로 나온다.

### 접두사 세 개

| 접두사 | 붙이는 곳 | 예 |
|---|---|---|
| `source#` | 행위를 **하는** 쪽 캐릭터 프롬프트 | `source#sex` · `source#hug from behind` · `source#cum in pussy` · `source#ejaculation` |
| `target#` | 행위를 **당하는** 쪽 캐릭터 프롬프트 | `target#sex` · `target#hug from behind` · `target#cum in pussy` · `target#male penetrated` |
| `mutual#` | **상호작용** — 양쪽에 | `mutual#eye contact` |

**같은 행위는 양쪽에 짝으로 적는다.** 뒤에서 안고 하는 구도라면 —

```text
캐릭1 : source#hug from behind, source#sex, source#cum in pussy
캐릭2 : target#hug from behind, target#sex, target#cum in pussy
```

- `mutual#eye contact` 는 `eye contact` 만 써도 되지만 **강제성을 조금 더 준다**
- `source#mating press` / `target#mating press` 만으로 NAI3 시절 엄청난 노력이 필요하던 구도가 꽤 잘 나온다
- `target#male penetrated` 는 남성이 당하는 상황에 쓰며 **장내·구강 어느 쪽이든 통한다**
- 사정은 싸는 쪽에 `source#ejaculation`, 받는 쪽에 `target#cum in ass` 처럼 **방향으로 갈라 적는다**

### 캐릭터 위치 격자 — 타율에 크게 영향을 준다

프롬프트 입력칸 **바로 아래 격자**에서 캐릭터 위치를 지정하는데, 생각보다 결과가 크게 갈린다.

```text
2인 기본     □ Ch1 □ Ch2 □        한 칸 띄운다
밀착 구도    □ Ch1 Ch2 □          붙인다
뒤에서 안기  세로로 붙인다
3인 구도     □ 박1 · 박힘 · 박2 □   셋을 다 붙인다
껴안기       세 명을 다 붙인다
```

### 접두사만으로는 자세가 안 잡힌다 — 보조 태그 배정표

| 구도 | 하는 쪽 (`source#`) | 당하는 쪽 (`target#`) |
|---|---|---|
| **들박** (서서 안고) | `source#carrying person` — 부족하면 `grabbing girl's (boy's) legs` | `target#carrying person` — **`standing` 을 빼면 타율이 많이 오른다** |
| **앉은 자세 삽입** | `sitting` | **`on bed` 를 붙이지 않는 편이 타율이 높다** |
| **후타 × 남** | `source#anal, source#sex, source#cum in ass, source#ejaculation` + `grabbing boy's legs, sitting` | `target#anal, target#sex, target#cum in ass, target#male penetrated` + `lying, on back, on bed` |

| **여캐 2 + 남캐 1 껴안기** | 여캐 둘에게 `source#arm hug` | 남캐에게 `target#arm hug` |
| **어깨 위에 태우기** | 태우는 쪽 — **상대적으로 클수록 확률이 오른다** | — |

**3인 구도 배정표** (가운데가 당하는 쪽)

### 자세 미세 조정

- 자세가 그래도 안 나오면 **`from side` 같은 시점 태그로 조절**한다
- 당하는 쪽에 `on stomach` → 고개를 숙인다. `lying, on stomach, on bed` → 자세가 뒤집힌다

## 7. 가이던스(=CFG) 는 얼마가 맞나 — 4.5 full 실사용 보고

## 8. 캐릭터를 원하는 대로 만들기
<small>2026-02 기준 · 근거 1건</small>

**인원 선언은 공식이 아니라 뼈대다.** 상단의 `1girl` 자리에 캐릭터 태그나 특징을 직접 박아도 된다.

- `misaka mikoto` 만 쓰면 미사카의 원래 체형이 그대로 나온다
- `1 skinny girl, misaka mikoto` 로 쓰면 **마른 체형이라는 뼈대 위에 미사카를 덮어쓰므로** 캐릭터의 원래 체형과 무관하게 마른 체형이 된다

다만 뼈대에 살을 덕지덕지 붙인다고 좋아지지는 않는다.

**두 캐릭터를 다룰 때**
- `exactly two characters` 를 **캐릭터 선언 태그보다 위에** 넣는다
- 베이스 프롬프트에 **`solo` 를 넣으면 안 된다** — 한 캐릭터만 등장할 때 쓰는 태그라 AI 가 혼자 있는 것으로 인식한다
- 인원 정의가 흐릿하면 AI 가 캐릭터 수를 헷갈리거나 합쳐 버린다. 문제가 생기면 베이스에 `1 girl, 1 boy` 를 넣는다
- **3명 이상은 타율이 매우 나쁘다**

**태그에 소유자를 명시한다** — `standing, look of very angry` 처럼 오해하기 쉬운 태그는 `standing girl, sitting wolf`, `look of very happy girl` 처럼 누구의 특징인지 붙인다. 인간형 캐릭터에 안 쓰이는 태그(`no solid flesh` 등)는 AI 가 알아서 무시한다.

**베이스 프롬프트 vs 캐릭터 프롬프트**

| 상황 | 권장 |
|---|---|
| 간단한 이미지 | **캐릭터 프롬프트** |
| 두 캐릭터가 어느 공간에서 어떻게 움직이는지까지 세세하게 | **베이스 프롬프트에 몰아넣기** |

캐릭터 프롬프트에 세세한 내용을 넣다 보면 태그가 제대로 작동하지 않고 그림체가 날뛰거나 배경이 사라지는 일이 있다. 그리고 **두 캐릭터 프롬프트 중 한쪽 비중이 높으면 그 캐릭터가 나머지를 먹어** 다른 캐릭터가 사라질 수 있다.

**자연어를 쓸 때** — 써도 되지만 AI 가 문장을 그대로 이해한다고 생각하면 안 된다. 문장 안 단어들의 조합을 보고 이해하는 것이지 문맥을 정확히 파악하지 못한다. 그래서 불필요한 부분을 잘라내는 편이 효과가 좋다.

## 10. 인페인팅과 Anlas 아끼기

### 인페인트가 잘 되게 하는 원리

**수정 영역 대비 크롭 영역의 비율이 높을수록 잘 된다.** 그래서 배경 크기를 **150%** 적용해 원본 해상도를 높인 상태로 진행하면 부담 없이 진행할 수 있고 **Anlas 는 0 소모**다.
NAIA 익스텐션(고해상도 부분 인페인트 툴, `https://arca.live/b/aiart/174711559`)은 포토샵 없이 **원본 이미지에 정확히 합성하는 것까지** 해 주며, 타일 대신 원하는 영역을 클릭해 고를 수 있게 한다.

### Anlas 0 으로 아웃페인팅 효과 내기

NAI 에는 아웃페인팅 기능이 따로 없지만, **normal 해상도까지가 Anlas 무료 구간**이라는 점을 이용한 편법이 있다.

```
normal 해상도 : portrait 832x1216 / square 1024x1024 / wide 1216x832
```

1. 확장하고 싶은 그림을 i2i 베이스로 넣고 **스트렝스와 노이즈를 최소로** 한 뒤, 비율에 맞는 `small~~` 해상도로 바꾼다 → 작은 해상도의 같은 그림이 나온다
2. 그 작은 그림을 다시 i2i 베이스로 넣고 **해상도를 normal 로 올린다** → 캔버스에 빈 공간이 생긴다
3. 원본 그림을 원하는 위치로 옮긴다
4. **원본만 빼고 빈 공간을 전부 인페인트로 칠한** 뒤 프롬프트를 쓰고 새로 뽑는다
5. 아쉬우면 한 번 더 반복

**부작용** — 해상도를 계속 낮췄다 올리므로 찐빠가 좀 날 수 있다. 그게 싫으면 normal → large 로 올리면 되지만 Anlas 가 녹는다.

## 13. NAIA 쓰는 법의 핵심
<small>2026-03 기준 · 근거 2건</small>

제작자는 **NAIA 가 애초에 와일드카드를 쓰지 않으려고 만든 도구**이며 와일드카드가 목적이라면 더 나은 도구가 많다고 못박는다. 핵심은 **검색과 자동화** 두 가지다.

**흐름**
1. 등급을 정한다 — `General`(건전) / `Sensitive`(약간의 노출) / `Questionable`(상당한 노출) / `Explicit`(성적 행위)
2. 단부루 태그 규칙에 맞는 검색·제외 키워드로 1차 검색 (키워드는 **2~3개**가 적당)
3. **심층 검색**에서 결과 내 재검색으로 좁힌다 (예: `barefoot` 재검색 → 146만 개 중 8.3만 개 → `foot focus` 추가 → 6539개)
4. `[현재 결과를 메인에 할당]`
5. `[프롬프트 엔지니어링/자동화/프리셋]` 에서 선행·후행 고정 프롬프트와 전처리 옵션(작가명·작품명·캐릭터명·캐릭터 특징 제거)을 잡는다

**검색 규칙** — 부분 일치가 기본이라 `loli` 를 검색하면 `hololive` 도 걸린다. 정확 검색은 `*loli` 지만 비용이 커서 `loli` 로 한 번 좁힌 뒤 `*loli` 를 쓴다.

**기간 설정** — NAI 사용자는 `24.11`(2024년 11월까지 Danbooru Data), ComfyUI ANIMA 사용자는 `25.09` 권장.

**네거티브 문법** — 와일드카드나 프롬프트 앞에 마이너스를 붙이면 생성 단계에서 네거티브로 들어간다.

## 14. 로컬 WebUI 와 연동 (WEBUIA)
<small>2026-05 기준 · 근거 3건</small>

NAIA 는 같은 UI 로 로컬 WebUI 를 조종하는 **WEBUIA** 모드를 갖고 있다.

1. 쓰는 webui 의 `webui-user.bat` 의 `COMMANDLINE_ARGS` 에 `--api` 를 추가해 실행

```bat
set COMMANDLINE_ARGS=--api
```

2. 모델·VAE 를 세팅한다
3. webui 주소 `127.0.0.1:7860` 을 확인한다
4. WEBUI 전환 버튼을 눌러 연결설정에 입력하고 `Connect`

Forge Neo 쪽에서는 `--api` 를 넣었다는 전제로 NAIA 의 `API 메뉴 → WEBUI 탭`에서 확인 후 저장하면 바로 연결된다 → [설치와 환경 구성](install.md)

**주의**
- `wd1.4-tagger` 나 `ADetailer` 기능을 쓰려면 그 확장이 WebUI 에 **미리 설치**돼 있어야 한다
- WEBUIA 는 1.1 이후 사용자의 WebUI 에서 샘플러 목록을 그대로 불러온다. WebUI 1.9.0 부터 샘플러와 스케줄러가 분리돼 `DPM++ SDE Karras` 라는 항목 자체가 없어졌으므로 **못 불러오는 것이 정상**이다
- NAIA 에서 ANIMA 를 쓸 때는 체크포인트를 `unet` 폴더에 두고 `NAIA PARAMS` 하단의 `EPS` 를 `ANIMA` 로 바꿔야 한다

## 15. EXIF — NAI 짤은 거의 다 읽힌다
<small>2026-08 기준 · 근거 8건</small>

**NAI 로 만든 그림은 EXIF 보존 체크를 안 하고 올린 짤이라도 이미지 안에 정보가 거의 다 남아 있다.** 저장해서 NovelAI 화면에 끌어다 놓으면 프롬프트가 들어온다. 원본 PNG 가 아니라 드래그로 저장한 webp 여도 되고, 웹에서 웹으로 바로 드래그도 되며, 아카라이브뿐 아니라 인터넷 어디에 올라온 NAI 제작 짤이든 통한다. 안 되면 이미지를 한 번 클릭해 원본을 띄운 뒤 시도한다.

그 밖의 방법:
- **EXIF 뷰어 유저스크립트** — 템퍼몽키에 `https://greasyfork.org/ko/scripts/464214` 를 설치하면 클릭 즉시 프롬프트가 뜬다
- **메모장으로 열기** — EXIF 가 보존된 원본에만 통한다

뷰어가 아무것도 못 읽는 경우의 99% 는 업로더가 EXIF 보존 체크를 해제하고 올린 것이다. 채널에 올라온 EXIF 뷰어들은 대개 NAI 메타데이터 추출 방식까지 포함하고 있어 그런 짤도 뽑아 준다.

→ [국룰](kukroul.md) · [자원](resources.md)

### 지금의 표준 확인 경로 — `novelai.net/inspect`

2026년 질문글에서 반복적으로 안내되는 방법은 이쪽이다.

```text
https://novelai.net/inspect       ← 이미지를 넣으면 프롬프트·설정이 그대로 나온다
```

**겉보기에 메타데이터가 없어 보여도 살아 있는 경우가 많으므로, 태그를 짐작으로 채우기 전에 여기부터 통과시킨다.**
그림만 보고 프롬프트를 완전히 역산해 재현하는 것은 **사람이 할 수 있는 일이 아니니 기대를 접으라**는 것이
같은 질문에 달린 답이었다.

> ⚠️ **가장 흔한 실수** — 게시판에서 **축소된 미리보기 이미지를 저장하면 메타데이터가 날아간다.**
> 그림을 클릭해 **새 창에서 원본을 연 다음 PNG 형식으로** 받아야 한다.

**어떤 그림을 봐야 하나** — 채널에 올라온 그림 중에는 EXIF 가 지워진 것도 있지만
**'그림체 공유' 같은 제목으로 올라온 글의 그림은 십중팔구 살아 있다.**
시리즈물 연재자들은 *"AI 로 그리는 사람들끼리 파일 변환으로 정보를 숨기지 말고 공유하며 배우자"* 는 입장에서
포토샵을 거친 것만 빼고 **EXIF 원본 그대로** 올린다.

### 그리고 통째로 가져오기 — `import metadata`

```text
챈 NAI 탭에서 마음에 드는 그림  →  우클릭으로 새 창에서 열기  →  .png 다운로드
→  NAI 웹 화면에 드래그 앤 드롭  →  체크 후 [import metadata]
→  프롬프트와 설정이 통째로 들어온다
```

**NAI 입문의 표준 경로는 '0부터 배우지 말고 남의 EXIF 를 가져다 쓰다가 점점 자기 것으로 바꾸는 것' 이다.**

> ⚠️ 다만 남의 그림체를 그대로 쓸 때 대가가 있다 — **작가 태그를 아홉 명씩 섞은 그림체**가 흔한데,
> 그대로 쓰면 **호로화**(그림체가 특정 작가 쪽으로 무너지거나 인물이 늙어 보이는 현상)를 제어하는
> 별도 노하우가 필요하다고 배포자들이 미리 경고한다.

### ⚠ 캐릭터 레퍼런스는 EXIF 에 담기지 않는다

Anlas 를 아끼려고 마음에 든 결과의 설정을 저장·재사용하려던 질문에서 확인된 한계다 (1건, 2026-07).

| 무엇 | EXIF 로 복원되나 |
|---|---|
| 프롬프트·설정 | **된다** — 파일을 NAI 화면에 드래그 앤 드롭 (완전히 같은 그림은 시드까지 맞춰야 한다) |
| 무엇이 쓰였는지 확인만 | `https://novelai.net/inspect` 에 끌어다 놓으면 자세히 나온다 |
| **캐릭터 레퍼런스 이미지** | **안 된다.** 참조 이미지 자체가 EXIF 에 담기지 않아 **새 그림을 뽑을 때마다 다시 넣어야 하고 그만큼 Anlas 를 계속 쓴다** (질문자가 확인하고 수긍했다) |

즉 '작가·그림체 프롬 조합 → 캐릭터 특징과 옷 작성 → 캐릭터 레퍼런스 투입' 파이프라인에서
**Anlas 를 아낄 수 있는 것은 앞의 두 단계까지**다. 레퍼런스 단계는 매번 비용이 든다.
(같은 글에서 시작 이틀 만에 Anlas 가 7000 밖에 안 남았다는 사례가 나왔다 — 레퍼런스를 습관적으로 쓰면 빨리 소모된다.)

## 17. NAIA 의 모듈들 — Ollama 프롬프트 생성 · 의상 프리셋

### Ollama 프롬프트 생성 (버전 143+)

한글이나 영어 자연어로 원하는 구도를 적으면 **로컬 LLM 이 단부루/e621 태그 프롬프트로 바꿔 준다.**

해결된 오류 — 4b 모델에서 `Ollama API 오류 (HTTP 404)` 와 `{"error":"model '...' not found"}` 가 뜨던 것은 **Ollama 를 한 번이라도 API 모드로 호출해 본 사용자만 자동 다운로드가 동작하던 버그**였고 `git pull` 로 해결된다.

### 의상 프리셋 (버전 151+)

단부루 의상 태그를 조합해 가며 **실제로 존재하는 의상 조합**을 찾아 프롬프트로 만든다. NAI 를 쓰지 않아도 프롬프트 탐색 용도로 쓸 수 있다.

## 19. `rating:` 태그는 4단계이고, 필수가 아니다
<small>⚠️ 2025-03 기준 · 근거 1건</small>

레이팅은 **단부루(Danbooru)의 수위 등급 체계를 그대로 가져온 것**이고, 흔히 생각하는 전연령/19금 2단계가 아니라 **4단계**다.

```
rating:general       전연령
rating:sensitive     약간 선정적
rating:questionable  (nsfw 와 함께)
rating:explicit      (nsfw 와 함께)
```

같은 시드로 비교한 결과 **레이팅을 지정할 때와 안 할 때 외형·동작·색채가 확연히 달라졌다.** `nsfw` 태그만 넣고 민감 부위 태그 없이 의상 태그만 적으면 그림이 노골적으로 변하긴 해도 노출까지는 가지 않는다. 여기에 `rating:explicit` 을 붙이면 일부에서 실제 노출이 확인되고 더 노골적이 된다.

**작성자의 결론 — 레이팅 태그는 필수가 아니다.**

> 레이팅에만 의존하면 결과를 모델에게 통째로 맡기는 셈이라 원하는 그림이 안 나올 수 있다. 원하는 구도와 노출 부위를 태그로 직접 적으면 `nsfw` 만으로 충분하다.

**레이팅이 진짜 쓸모 있는 곳은 R-18 이 아닌 나머지 등급을 만들 때다.** 예를 들어 노출 정도를 어중간하게 조절하고 싶은데 NAI 에는 수치로 미세 조절할 수단이 없으므로, 이럴 때 레이팅 태그로 수위 단계를 잡는 것이 유용하다.

NAIA 의 '인원 수 / 이미지 목적' 4등급도 이 체계를 그대로 쓴 것이다.

## 21. Vibe Transfer 의 IE 와 RS — 값 하나하나가 무엇을 하나
<small>2026-08 기준 · 근거 4건 · 자료 엇갈림</small>

앞의 '레퍼런스 기능' 항목이 **어느 기능이 나은가**를 다뤘다면, 이 항목은 **슬라이더 두 개의 정체**다. NAI 4.0 기준 장문 실험 글에서 왔다.

```
결론  IE 는 닥치고 1.0.  RS 는 0.6 을 기준으로 프롬프트 강도에 따라 조절.
```

### IE (Information Extracted) — 원본에서 얼마나 가져올까

Vibe 원본에서 **얼마만큼의 정보를 반영하고 얼마만큼을 무작위로 돌릴지** 정한다.

| IE | 결과 |
|---|---|
| **1.0** | 그림체(눈매·턱선·선 형태)와 머리색이 잘 반영. 옷 길이·조명은 절반쯤 |
| 0.95 | 여기서부터 **그림체 일관성이 흔들린다** |
| 0.6 | 없던 스타킹이 튀어나온다 |
| 0.4 | 배경이 사라지고 의상 자유도가 급증 |
| 0.2 | 아예 다른 캐릭터가 나온다 |
| 0.05 | 배경 색채 정도만 남는다 |

### RS (Reference Strength) — 새 그림이 얼마나 따라갈까

프롬프트 강조값처럼 작동한다. **RS 1.0 이어도 재현도는 70~80% 수준**이다. 0.8 부터 눈 색이 바뀌는 등 원본 영향이 약해지고, 0.4 이하는 그림체 외 요소가 희미해지며, 0.05 에서는 NAI 기본 그림체로 수렴한다.

### 이 글의 가장 쓸모 있는 발견

> **프롬프트와 Vibe 가 충돌할 때 프롬프트를 따라가기 시작하는 RS 값은 그 태그의 단부루 게시글 수(태그 강도)에 좌우된다.**

| 태그 | 단부루 게시글 수 | 프롬프트가 이기는 RS |
|---|---|---|
| `annoyed` | 14k | **1.0** 에서 이미 10/10 |
| `+ +` | 31k | 0.8 에서 10/10 |
| `Indian style` | 16k | 0.8 에서 10/10 |
| `arched back` | 20k | 0.8 에서 10/10 |
| `sobbing` | **772** | 1.0 에서 **0/10**, 0.4 에서야 10/10 |
| `t-pose` | **428** | **0.1** 까지 내려야 10/10 |

즉 **약한 태그를 쓰면서 Vibe 를 강하게 걸면 그 태그는 아예 안 먹는다.** 의상 프롬프트는 강한 태그라도 RS 0.6 이하에서 급격히 타율이 오른다(`nightgown` 9.4k 조차 RS 0.6 에서 90%). 다만 **옷의 색만 바꾸는 것은 RS 1.0 에서도 100% 먹힌다.**

RS `0.75` 이하부터 프롬프트를 잘 따라가고 RS `0.4` 이하부터는 Vibe 그림체를 잘 안 따라간다 — **그 사이인 `0.6` 이 NAI 기본값인 이유가 여기서 설명된다.**

### 목적별 값 (원글쓴이 댓글)

```
구도·캐릭터 디테일을 많이 반영  →  IE 1.0 + RS 0.8 이상
그림체만 반영                  →  그림체 프롬프트를 빼거나 Vibe 와 유사한 것만 넣고 IE 1.0 + RS 0.4 이하
```

**단서 하나** — 작가 프롬프트를 잔뜩 넣어 쓰는 사람은 IE 를 늘 1 로 둬도 그림체 영향을 거의 못 느꼈다는 댓글이 있고, 원글쓴이도 **이미 프롬프트에 그림체 정보가 많으면 Vibe 의 그림체 정보가 큰 영향을 못 주는 것 같다**고 동의했다.

> **시점 주의 — 이 실험은 NAI 4.0 기준이고, 글을 쓰는 도중 4.5 가 나왔으므로 4.5 의 Vibe 는 다를 수 있다고 원글쓴이가 명시했다.**

### 야짤로 넘어가면 그림체가 바뀔 때 — Vibe 로 교정한다 (2025-04, V4)

같은 작가 태그를 유지해도 **NSFW 태그를 붙이면 그림체가 눈에 띄게 달라지는** 현상이 있다.
붙이는 태그 덩어리가 복잡해질수록 이탈이 심해진다. 대처는 **그 그림체로 미리 뽑아 둔 건전한 그림 4장을 Vibe 로 먹이는 것**이다.

```text
RS  낮게  (0.1 수준도 무방)  — 높으면 구도·자세·색감까지 따라가 자유도가 죽는다
IE  높게                     — 낮으면 그림체 보존이 안 돼 Vibe 를 쓰는 의미가 없다
```

**⚠️ 공식 안내와 실측이 어긋난다 — 양쪽을 적어 둔다.**

| 쪽 | 말 |
|---|---|
| **공식 패치노트** | IE **총합**이 1 을 넘으면 안 된다 |
| **실측 (1건, 2025-04)** | 그림체 보존이 목적이면 **4장 모두 1** 로 두지 않으면 보존 효과가 떨어진다 |

위 IE 표에서 `1.0` 아래로 내려가면 그림체 일관성이 바로 흔들리는 것과 방향이 같다.

**먹이는 건전짤에 남성 캐릭터가 들어 있어야 1대1 성인 구도의 타율이 크게 오른다.**
여성 캐릭터만 들어간 그림을 먹이면 남성 쪽이 계속 뭉개진다.

> **반례 — 애초에 안 생기게 할 수도 있다.** 야짤에서 그림체가 바뀌는 정도는 **작가 조합 자체의 차이**가 커서,

## 23. 만화(코마) 뽑기 — 2컷 · 3컷 · 4컷
<small>⚠️ 2025-03 기준 · 근거 3건</small>

NAI V4 의 **캐릭터 위치 지정 기능**으로 만화(코마) 형식을 뽑을 수 있다. 2025-03 에 2컷 → 3컷 → 4컷 순으로 세 글이 나왔다.

### 2컷 — 최종판은 토큰을 줄이는 것이다 (타율 약 80%)

첫 판은 태그를 길게 나열했는데(`2girls, 2koma, comic, speech bubble, white border, multiple views`),
**개선 최종판의 핵심 변화는 토큰을 크게 줄인 것**이다.

```text
프롬프트        :  {{comic, 2koma}}, {{speech bubble}}
캐릭터 프롬프트  :  {{{border}}}
캐릭터 네거티브  :  {{{{{{{outside border}}}}}}}
```

**캐릭터 프롬프트의 `border` 와 캐릭터 네거티브의 `outside border` 조합이 각 캐릭터를 자기 칸 안에 가둬 컷 침범을 막는다.**
(`{}` 는 NAI 의 V3 레거시 강조 문법으로 겹칠수록 세진다 → 위 "프롬프트 문법" 절.)
동인지 작가 태그를 넣으면 타율이 더 오른다. 캐릭터 위치 지정에서 캐릭터를 위/아래로 배치하고 각 컷의 액션을 캐릭터 프롬프트로 준다.

### 3컷 — `3koma` 는 안 먹는다

> **`3koma` 태그는 이론상 맞지만 실제로는 안 먹는다. 세 컷을 원하면 `4koma` 를 넣어야 타율이 높다.**

3컷은 컷 간 프롬프트 침범이 2컷보다 심하므로 네거티브를 잘 넣어야 한다.

### ⚠️ 셋 다 공통 — 세로 길이가 제일 중요하다

|---|---|
| `1472x1472` 정사각형으로 키우기 | **실패** |

| 가로 배치(왼쪽/오른쪽 컷) · `1 / 1 1` 같은 비대칭 배치 | 안 먹혔다 |

### 4컷 — 태그의 역할이 나뉜다

```text
{{comic}}, greyscale, speech bubble, emphasis lines, multiple views
```

| 역할 | 태그 |
|---|---|
| **만화다운 느낌**을 낸다 | `greyscale`, `emphasis lines`(만화의 집중선), `speech bubble` |
| **컷 분할 타율**을 올린다 | `{{comic}}`, `multiple views` |

캐릭터 프롬프트마다 `border`, 캐릭터 네거티브에 `outside border` 를 넣으면 타율이 오르고,
**위치 지정은 많이 해 줄수록 타율이 오르는 느낌**이라고 한다. 타율은 10번에 두세 번 정도다.

### ⚠️ 그런데 — 원글쓴이 본인이 이렇게 말했다

> **2컷 정도는 그냥 인페인팅이 타율도 좋고 더 빠르다.**

만화 프롬프트 글을 쓴 사람이 댓글에서 직접 인정한 것이다. **컷 수가 적으면 프롬프트로 씨름하지 말고 인페인팅으로 가라.**

## ⚠ NAIA — 설치하고 '자동 생성' 을 바로 누르면 안 된다
<small>2025-11 기준 · 근거 1건</small>

**입문자가 거의 100% 걸리는 함정이다.** 설치 직후 자동 생성이나 랜덤 프롬프트를 바로 누르면
**'그림체 없는 랜덤 태그 짤' 만 나오고 왜 그런지 알 수가 없다.**

### 무슨 일이 일어나는가

> 자동 생성은 **'프롬프트 고정' 을 켜지 않으면 자동으로 랜덤을 굴린다.**
> 그런데 이때 굴려지는 것은 **비어 있는 '프롬프트 엔지니어링' 내용**이고,
> **그것이 메인 프롬프트를 통째로 덮어써 버린다.**

즉 내가 메인 칸에 적어 둔 그림체·캐릭터가 **지워지는 것**이다. 프로그램이 고장 난 게 아니다.

| | |
|---|---|
| **네거티브는 안전하다** | 메인 프롬프트 **옆의 네거티브 칸**에 적으면 랜덤에 덮이지 않고 계속 유지된다 |
| **덮이지 않게 하려면** | '프롬프트 고정' 을 켜거나, 아래의 **선·후행 고정 프롬프트**에 넣는다 |

### 선행 / 후행 고정 프롬프트 — 여기에 넣으면 안 지워진다

'프롬프트 엔지니어링/자동화/프리셋' 창의 두 칸이 핵심이다. **랜덤/다음 프롬프트를 눌러도 바뀌지 않는다.**

| 칸 | 넣는 것 |
|---|---|
| **선행 고정 프롬프트** | 와일드카드 · 캐릭터 관련 프롬프트 |
| **후행 고정 프롬프트** | **그림체와 퀄리티 프롬프트** |

```text
선행 예시 :  nsfw, 1girl, __대분류__, __사정여부__, __배경_의상__, (그림체 프롬)
```

### 나머지 필수 설정 넷

| 기능 | 무엇 |
|---|---|
| **자동 숨김 프롬프트** | 2차 필터링. 랜덤으로 뽑히는 태그 중 보기 싫은 작은 태그(예: 피어싱)를 **아예 태그로 쓰지 않게** 만들어 네거티브보다 확실하게 걸러낸다 |
| **랜덤 작가명 제거** (프롬프트 전처리) | **특정 그림체를 쓴다면 사실상 필수다.** 안 끄면 랜덤 작가가 그림체를 덮는다 |
| **와일드카드 단독 모드** | 캐릭터를 고정하려면 NAID4 캐릭터 탭에 캐릭터 프롬프트를 넣고 **이것을 켠다.** 끄면 랜덤 캐릭터가 섞인다 |
| 와일드카드 적용 | 받은 파일을 와일드카드 폴더에 넣은 뒤 **와카 모듈에서 '리로드' 를 눌러야** 적용된다 |

**NAI 본체는 캐릭터를 5개까지만 넣을 수 있지만 NAIA 는 무제한이다.**

> ⚠️ **프리셋의 한계 (댓글 확인)** — 프리셋은 **프롬프트만 저장하고 가이던스·리스케일 값까지는 따라오지 않는다.**
> 세팅이 그대로일 거라 믿고 프리셋을 바꾸면 결과가 달라진다.

## ⚠ 작가 프롬프트는 뒤쪽에 둘수록 강하다 — 통설과 반대다
<small>2026-07 기준 · 근거 3건 · 자료 엇갈림</small>

**비직관적이라 반드시 짚고 넘어가야 하는 규칙이다.**

> NAI 에서 작가 프롬프트는 **뒤쪽에 배치될수록 강하게 적용된다.**
> **가중치를 3 이상 줘도 안 되던 것이 위치만 바꾸니 원하는 대로 나온 사례**가 있다 (1건, 2025-10).

### 왜 헷갈리는가

일반적으로 통용되는 말은 정반대다 — A1111 계열 해설은 **"프롬프트의 위치 자체도 가중치라서 앞에 둘수록 주의를 더 받는다"** 고 한다.
그래서 작가 태그를 맨 앞에 몰아 두는 습관이 굳어 있는데, **NAI 의 작가 태그에서는 그 감각이 뒤집힌다.**

### 로컬에서도 같은 결론이 나왔다

로컬 ComfyUI·WAI-NSFW 환경에서 작가 조합 **300장을 채점한 실험**의 결론 중 하나가 이것이다
(→ [프롬프트 쓰는 법](prompting.md) 의 '작가 태그를 어떤 순서로 늘어놓나').

> **목표로 하는 화풍의 작가를 최후열에 배치하고, 화풍이 유사한 작가를 역순으로 배열**하면 가장 좋다.

**NAI 와 로컬 양쪽에서 같은 방향의 보고가 나왔다는 점이 이 규칙의 근거를 세운다.**
반대로 **등록 수는 많으나 화풍 차이가 큰 작가는 가중치를 높여 최대한 앞쪽에** 두는 것이 안정적이라는 것도 같은 실험의 결과다.

> 가중치가 안 먹는 느낌이면 위치를 먼저 바꿔 보고, 그다음에 `::` 앞 공백을 확인한다
> (→ [프롬프트 쓰는 법](prompting.md) 의 가중치 절).

### ⚠ 그런데 2026-07 에 반박이 나왔다 — 양쪽을 병기한다

NAI 4.5 그림체 스택을 공유한 글의 본문은 위와 같은 취지였다 —
*"작가 태그를 앞보다 뒤에 두는 게 효과가 좋은 것 같다, 맨 앞과 맨 뒤가 가장 반영이 잘된다고 들었다."*
스택은 작가 11명에 최대 가중치 `6.9::shnva::` 까지 주는 것이었다.

> **댓글은 위치 차이가 크지 않다고 반박했다.** 그리고 더 중요한 것을 짚었다 —
> **`geraurgos` · `sikosiya` 는 NAI 4.5 에 아예 학습되지 않은 것 같고, 빼도 결과가 똑같다.**

| 쪽 | 말 | 시점 |
|---|---|---|
| 2025-10 관찰 + 로컬 300장 채점 | **뒤쪽에 둘수록 강하다** | 2025-10 · 2025-11 |
| 2026-07 댓글 | **위치 차이는 크지 않다.** 그보다 **스택에 든 작가가 실제로 학습돼 있는지**가 결과를 가른다 | 2026-07 |

**실무 순서는 위치 조정이 아니라 '한 명씩 빼서 확인' 이 먼저다.** 없는 작가 태그는 가중치만 낭비한다

### 네거티브에 작가 태그를 박아 두는 것이 그림체를 망친다

## 학습되지 않은 마이너 캐릭터 뽑기 — 옆에 원작을 붙여 놓고 인페인트

## 반실사에 NSFW 얹기 — 순서가 전부다
<small>⚠️ 2025-06 기준 · 근거 1건</small>

NAI 4.5 웹에서 **Anlas 를 쓰지 않고**(일정 해상도·설정 이하면 무제한 무료) 반실사 그림체에 캐릭터와 NSFW 를 넣는 절차다 (1건, 2025-06).
한 사이클에 30분 정도면 충분하고, 그림체를 한 번 찾으면 핀업으로 캐릭터만 바꿔 가며 쓸 수 있다.

### 1단계 — 그림체와 퀄리티부터. **NSFW 는 절대 넣지 않는다**

옷도 너무 야한 것은 좋지 않고 인스타 인플루언서 옷차림 정도를 참조한다.
이 단계에서 원하는 구도·그림체가 나온 이미지를 **시드용·참조용으로 많이 저장**한다.

| 참조 이미지 조건 | |
|---|---|
| 배경 | **없는 편이 좋다** |
| 해상도 | **업스케일하지 않고 결과물과 같은 해상도**로 — 해상도에 따라 그림체가 바뀌기 때문이다 |

초반 랜덤 뽑기에는 i2i 보다 **핀업(pin-up)** 기능이 다양한 구도·그림체를 준다.

### 2단계 — i2i 로 구도를 잡고 시드로 그림체를 굳힌다

`Strength` **0.8 이상**을 주면 구도를 바꿀 수 있고 그때 흐트러진 그림체는 시드로 보완한다.
시드로 쓰는 이미지는 번호만 쓰는 것이라 완성도는 상관없고 요소가 중요하다.
엉뚱한 요소가 튀어나오면 `Prompt Guidance` 와 `Prompt Guidance Rescale` 을 조금씩 조정한다 (예: Guidance `-0.4`, Rescale `+0.3`).
**특정 캐릭터를 넣고 싶으면 이 단계에서 약하게** 캐릭터 요소를 넣어 둔다.

### 3단계 — **마지막에** 세부 프롬프트와 NSFW 요소를 넣는다

**이 단계에서 넣어야 그림체를 크게 바꾸지 않고 적용된다.** 시드와 이미지 세팅은 건드리지 않는 것이 그림체 유지에 좋다.
실패하면 2단계로 돌아간다.

> ⚠️ **중요한 경고** — **NSFW 프롬프트는 검열 때문에 순서만 바뀌어도 그림체가 망가지기도 한다.**
> 그래서 NSFW 강도를 자유롭게 조절할 수 있게 되기 전까지는 **2D 나 웹툰 그림체로 NSFW 프롬프트를 따로 연습해 최적화한 뒤 복사해 붙이라**는 것이 권고다.

### 포인트를 쓰는 경로

| 원하는 것 | 기능 |
|---|---|

## 규제와 결제 — NAI 가 버티는 방식, 그리고 진짜 위험
<small>2026-04 기준 · 근거 1건</small>

|---|---|
| **NSFW 는 공식 기능이 아니다** | 공식 사이트·문서 어디에도 언급이 없다. 공식 안내는 **'V4.5 Curated 로 원하는 결과가 안 나오면 V4.5 Full 을 써 보라'** 는 식으로만 말한다 — Full 이 Curated 가 못 하는 것을 한다고 했을 뿐 NSFW 를 만든다고 말한 적은 없다. **단부루 작가 태그로 그림체를 흉내 내는 것도 공식 기능이 아니며, 공식 태그 자동완성은 작가 태그도 NSFW 태그도 완성해 주지 않는다** |

## EXIF 를 그대로 복사했는데 결과가 다르다 — `Curated` 와 `Full` 은 다른 모델이다
<small>2026-08 기준 · 근거 2건</small>

마음에 드는 그림의 EXIF 를 통째로 붙여 넣었는데 전혀 다른 그림이 나온다는 질문의 원인이 한 줄로 밝혀졌다 (2026-08).

> EXIF 의 **`Source`** 항목이 `NovelAI Diffusion V4.5 C02D4F98` — 즉 **V4.5 Curated** 였는데
> 질문자는 **Full** 로 돌리고 있었다. **Curated 로 바꾸자 해결됐다.**

**`Curated` 는 나체·성교 표현을 제거한 별개 판본이다.**
프롬프트·시드·스텝을 전부 맞춰도 모델이 다르면 결과가 달라진다.
**EXIF 복사로 재현할 때 가장 먼저 볼 것이 `Source` 다.**

|---|---|

| Resolution | `896x1152` ↔ `832x1216` |

| **Prompt Guidance Rescale** | `0.4` ↔ `0` |
| Undesired Content Strength | 둘 다 `0` |
| Character Prompt | 별도 칸이므로 **따로 옮겨야 한다** |

### 곁들여 볼 만한 것 — 원본 프롬프트의 구성

같은 글에 실린 프롬프트가 작가 태그 혼합의 실물 표본이다.

```text

## 2026년 질문글에서 반복해서 나온 것들
<small>2026-07 기준 · 근거 7건</small>

### 태그의 **위치**가 결과를 바꾼다 — 논리보다 되돌리기 테스트

프롬프트를 '정리' 했더니 오히려 나빠진 사례다 (2026-05).

**특정 캐릭터에서만 단색 배경 + 단색 남성**이 나오게 됐고 다른 캐릭터는 멀쩡했다.

> **같은 태그라도 Base 에 있느냐 Character 에 있느냐에 따라 찐빠가 나기도 하고 잡히기도 하며,
> 그림체에 따라서도 다르게 반응한다. 구조적 논리를 찾기보다 하나씩 되돌리며 최적 위치를 테스트하는 편이 현실적이다.**

**색을 직접 적지 않았는데 특정 색이 자주 나온다면 보통 그 색을 많이 쓰는 작가 태그가 섞여 있는 것이다.**

## NAIA 조건부 문법 — `1girl` 보다 앞에 태그 넣기
<small>2026-03 기준 · 근거 1건</small>

NAIA(NAI Auto Generator) 1.5 의 랜덤 기능은 `boy`/`girl` 계열 인원수 태그를 **무슨 짓을 해도 프롬프트 맨 앞으로 밀어낸다.**

```text
1) NAIA 가 받아오는 1girl / 1boy 같은 고정 태그를  #  를 붙여 무효화한다
2) # 가 붙어도 조건부(conditional)는 여전히 반응하므로,
   각 인원수 태그에 대응하는 조건식을 만들어 원하는 태그를 앞쪽에 재삽입한다

```text
(fur dataset&~1boy&~boys):1girl=fur dataset^1girl,
(fur dataset):1boy=#1boy,
(fur dataset):2boys=#2boys,
(fur dataset):3boys=#3boys,
(fur dataset):4boys=#4boys,
(fur dataset):5boys=#5boys,
(fur dataset):6+boys=#6+boys,
(fur dataset&1boy):1girl=fur dataset^1girl^1boy,
(fur dataset&2boys):1girl=fur dataset^1girl^2boys,
(fur dataset&3boys):1girl=fur dataset^1girl^3boys,
(fur dataset&4boys):1girl=fur dataset^1girl^4boys,
(fur dataset&5boys):1girl=fur dataset^1girl^5boys,
(fur dataset&6+boys):1girl=fur dataset^1girl^6+boys,

| 기호 | 뜻 |
|---|---|
| `#` | 그 태그를 무효화 (조건부는 여전히 반응한다) |
| `(조건):대상=치환결과` | 조건부 문법 |
| `&` | AND |
| `~` | NOT |
| `^` | 연결 |

## NAIA 시퀀스 문법 — `:begin ~ :end` 로 연작을 한 번에
<small>2026-07 기준 · 근거 1건</small>

NAIA(NAI 자동화 툴)에는 **한 번 실행으로 연작을 뽑는 시퀀스 문법**이 있다 (1건, 2026-07, NAI Diffusion 4.5).
21장짜리 연작을 한 번에 뽑은 실제 시퀀스 전문이 공유돼 있다.

### 구조와 붙이는 자리

```text
:begin
:seq, <1컷 프롬프트>
:seq, <2컷 프롬프트>
   …
:end
```

**이 덩어리를 NAIA 의 '랜덤 프롬프트' 칸에 붙여 넣는다.** 배치 순서는

```text
[그림체 or 선행 고정]  →  [ :begin ~ :end 본문 시퀀스 ]  →  [퀄리티 or 후행 고정]
```

작성자가 댓글로 확인해 줬고 질문자도 실제로 문제없이 됐다고 답했다.

### 컷마다 바뀌는 것 — 해상도까지 바꾼다

```text
resolution:960x1088      세로 컷
resolution:1024x1024     정사각 컷
resolution:1216x832      가로 컷
```

**연작 안에서 컷마다 화면비를 바꿀 수 있다는 것이 이 문법의 핵심 값어치다.**
